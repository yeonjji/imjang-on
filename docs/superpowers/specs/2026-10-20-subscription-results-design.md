## 2. 데이터 모델

```prisma
/// 청약 공고 1건의 공식 결과(청약홈). 원 응답을 오퍼레이션별로 보관하고, 화면은 이 원값에서 계산한다.
model SubscriptionResult {
  noticeId   BigInt   @id
  /// 'ok' | 'empty'(결과 없음) | 'api_error'
  status     String   @db.VarChar(12)
  competition Json?   // 경쟁률 오퍼레이션 data[]
  scores      Json?   // APT 가점 data[]
  special     Json?   // APT 특별공급 data[]
  fetchedAt  DateTime
  @@index([status])
}
```

## 3. 수집

- `scripts/ingest/subscription-results/`. 기존 `subscriptions` 잡 뒤에 붙여 같은 타이머로 매일 실행한다(새 타이머 없음, `run-etl.sh` subscriptions 블록에 한 줄 추가).
- **대상:** 주택관리번호가 있고 `receiptEnd`가 지난 공고 중 다음 조건인 것.
  1. 결과 행이 없는 공고(처음 수집). 처음 한 번 전체 약 6,100건을 받는다(공고당 1~3번 호출).
  2. `winnerDate` + 30일 이내 공고는 매일 다시 받는다. 원문에 "은행 전산 사정으로 접수건수가 변동될 수 있다"고 되어 있기 때문이다.
  3. `empty`는 `receiptEnd` + 30일 안이면 다시 받는다(결과 공개 지연 대비).
- 개발계정 한도는 하루 4만 건이라 충분하다. 동시성 2. 한도 초과 시 즉시 중단(1단계와 같은 구조).

## 4. 화면 (UI 시안에서 확정)

- **위치:** 청약 상세 `UnitSupplyTable`(공급 세대) 바로 아래, id `results`, 사이드바 "청약 결과".
- **숨김:** 접수 전이거나 결과가 없으면(`status !== 'ok'` 또는 데이터 0행) 섹션을 숨긴다. 예측값은 만들지 않는다.
- **APT:**
  1. 요약: "1순위 해당지역 전체 487.09대 1 (임장ON 계산: 접수 합 ÷ 공급 합) · 최고 59.98㎡ 1,692.33대 1"
     - 최종 미달이 있으면 "최종 미달 545세대"를 덧붙인다(주택형별 마지막 행의 △ 합).
  2. 주택형별 표: 공급 · 1순위 해당지역(접수, 경쟁률) · 1순위 기타지역 · 2순위(있을 때만). 경쟁률은 공식값 그대로, 미달은 '미달 n세대', '-'는 '—'.
  3. 당첨가점(주택형 × 지역, 최저·평균·최고): 0이나 '-'인 행은 숨긴다. 표 전체가 비면 블록을 숨긴다.
  4. 특별공급 유형별: 배정 · 접수 · 경쟁률(임장ON 계산). 배정 0인 유형은 숨긴다.
- **오피스텔·도시형 / 잔여 / 임의:** 주택형별 공급 · 접수 · 경쟁률(공식값) 한 표. 공공지원민간임대는 공급유형(일반·신혼부부·청년·고령자) 열을 추가한다.
- **출처:** "한국부동산원 청약홈 · {조회일} 조회" + "은행 전산 사정으로 접수건수가 일부 변동될 수 있으며, 최종 결과는 청약홈에서 확인하세요."
- **표시하지 않는 것:** 당첨 가능성, 다른 공고·지역 평균과의 가점 비교(검토 ⑦), 15110812 지역 통계.

## 5. 테스트

- **유닛:**
  - 경쟁률 문자열 파서: 숫자·쉼표·'-'·'(△n)'·빈 값
  - 주택형 표기
  - 요약 합산: 주택형당 공급 1회, 1순위 해당지역 접수 합
  - 최종 미달 합
  - 가점 0·'-' 숨김
  - 특별공급 유형별 합산(기관추천 제외)
  - 유형별 표 모델
- **통합:** 수집 대상 선정(처음·재수집 기간·empty 재시도), 한도 중단, 저장
- **렌더링:** 유형별 블록, 미달 표기, '—' 표기, 안내 문구, 금지 문구('당첨 가능', '유리') 부재
- **e2e:** 시드 공고 1건(APT)에 결과 행을 넣고 섹션 렌더 확인
- **실데이터 QA:** 경쟁 공고·미달 공고·오피스텔 공고 각 1곳
