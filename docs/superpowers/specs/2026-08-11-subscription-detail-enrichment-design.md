### 1.2 진짜 문제

`app/(public)/subscription/[id]/page.tsx`는 위치가 있으면 지도·**주변 단지 실거래가**(`getNearbyApartments`)·지하철·생활 인프라를 렌더한다. 위치가 없으면 그 자리에 문구 하나만 남는다.

> 위치 정보가 없어 주변 실거래가·편의시설 정보를 제공하지 않습니다.

**즉 얇은 것은 위치 없는 2,367건이다.** 이들은 공급표 + 공용 FAQ + 공용 블록뿐이라 서로 near-duplicate다.

그런데 이 2,367건 중 **2,364건이 주소를 갖고 있다.**

⚠️ **2026-08-12 정정.** 처음에는 "어댑터가 `lat: null`을 하드코딩하고 지오코딩을 호출하지 않는다"고 적었으나
실제로는 `scripts/ingest/subscriptions/runner.ts:69`가 이미 `geocode(notice.address)`를 부르고 있었다.
어댑터의 `lat: null, lng: null`은 정규화 기본값이고, 좌표가 비는 진짜 이유는 **질의가 원문 주소라서**다.
청약 주소가 `경기도 김포시 고촌읍 신곡리 김포신곡6지구 도시개발사업구역 A3BL` 같은 사업지구 서술형이면
카카오 주소검색이 못 찾는다. 결과(좌표 없음)는 같지만 고칠 지점이 다르다 — 배선이 아니라 질의다. `scripts/ingest/geocoder.ts`의 `geocode()`와
`scripts/ingest/amenities/geocode-fill.ts`의 `enrichWithGeocode()`는 이미 있고 병원·약국 적재가 쓴다.
`KAKAO_REST_KEY`도 운영 박스에 설정돼 있다(실측).

### 1.3 noindex는 이 문제를 풀지 못한다

애드센스 심사는 자체 크롤러(`Mediapartners-Google`)를 쓴다. `noindex`는 심사에 보이지 않고,
`Mediapartners-Google`은 robots.txt의 `*` 규칙도 무시한다(`docs/adsense/` 딥리서치 확증).
**표면을 줄이려면 404/410으로 실제 비공개여야 한다.** D1·D2b가 410을 택한 이유와 같다.

## 2. 확정된 방침

| 논점 | 결정 | 근거 |
|---|---|---|
| 축소 먼저인가 보강 먼저인가 | **지오코딩 백필 먼저** | 지우려는 대상의 대부분이 "주소는 있는데 좌표만 없는" 페이지다. 먼저 지우면 살릴 수 있는 것을 잃는다 |
| 무엇으로 고유성을 만드나 | **분양가 × 지역 실거래 결합** | 재료가 이미 전 건에 있다. 원출처(청약홈)에 없는 결합이다 |
| 면적당 단가 비교 | **하지 않는다** | `SubscriptionUnit.area`의 기준이 행마다 다르다(공급 80% / 전용 12%). 실거래는 전용면적이라 단가를 나란히 두면 행끼리도, 실거래와도 비교가 안 된다 |
| 면적 표기 | **셀마다 기준을 병기** (`공급 82.86㎡`) | 일괄 "공급면적"으로 적으면 12%가 거짓이 된다 |
| noindex | **쓰지 않는다** | 애드센스 심사에 보이지 않는다 |
| 축소 기준 | **지오코딩까지 실패한 공고만 410** | 데이터가 대상을 정하게 한다. 사람이 미리 선을 긋지 않는다 |

### 2.1 명시적으로 하지 않는 것

- **LLM으로 요약 문장을 생성하지 않는다.** 자동 생성 텍스트를 늘리는 것이 애드센스 거절의 원인이었다.
- **`noindex` 일괄 적용을 하지 않는다.** 검색 위생에는 듣지만 이번 목표가 아니다.
- **경쟁률·당첨 가점 데이터를 가져오지 않는다.** 보유하지 않았고 이번 범위 밖이다.

## 3. 아키텍처

세 단계를 순서대로 실행한다. 앞 단계의 결과가 뒤 단계의 대상을 정한다.

```
1단계  지오코딩 백필     2,364건 시도 → 성공분은 지도·주변실거래·인프라가 자동으로 붙는다
                        (페이지 코드는 이미 coord 유무로 분기한다 — 수정 불필요)
2단계  분양가 비교 블록   5,911건 전부에 공고마다 다른 수치
3단계  축소 + changefreq  1단계 실패분만 410, 마감 공고 changefreq 교정
```

1단계는 **페이지 코드를 건드리지 않는다.** `page.tsx`가 이미 `coord ? … : …`로 분기하므로
DB의 `location`만 채우면 지도·주변 단지·지하철·인프라가 그대로 살아난다.

## 4. 1단계 — 지오코딩 백필

### 4.1 스크립트

`scripts/ingest/subscriptions/geocode-fill.ts` (신규)

- 대상: `location IS NULL AND address IS NOT NULL` (2,364건)
- 쿼리: `buildGeocodeQuery(regionName, address)` — 시도·시군구 접두사로 동명 지역 모호성 제거
- `--dry-run` 기본, 성공률과 검증 실패 사유를 집계해 출력. `--apply`로 반영
- 카카오 API 호출 간 간격을 둔다(기존 `geocode-fill.ts`의 방식을 따른다)

### 4.2 좌표 검증 — 이 설계의 핵심 안전장치

카카오 응답의 `region1`(시도)·`region2`(시군구)가 공고의 `regionName`과 어긋나면 **버린다.**

엉뚱한 좌표가 들어가면 그 페이지의 주변 실거래·인프라·지하철이 통째로 다른 동네 것이 된다.
빈 페이지보다 나쁘다 — 틀린 정보를 사실처럼 싣게 된다.

검증 방식:

- `regionName`을 공백으로 쪼갠다. 첫 토큰을 시도, 둘째 토큰을 시군구로 본다.
- 시도는 항상 비교한다. `서울`/`서울특별시`처럼 표기가 다를 수 있으므로 **한쪽이 다른 쪽의 접두사면 일치**로 본다.
- 둘째 토큰이 없으면(단일 토큰 `regionName`) 시도만 비교한다.
- 어느 한쪽이라도 어긋나면 `location`을 쓰지 않고 실패로 집계한다.

### 4.3 어댑터 배선

`adapter-applyhome.ts`·`adapter-lh-presub.ts`의 `lat: null, lng: null` 하드코딩을 걷어내고
적재 시 지오코딩한다. 이걸 하지 않으면 앞으로 들어오는 공고가 같은 문제를 반복한다.

## 5. 2단계 — 분양가 비교 블록

### 5.1 무엇을 보여주나

```
이 공고의 분양가와 주변 시세

주택형    면적            분양 최고가
59A      공급 82.86㎡     1억 9,380만원
84A      공급 112.4㎡     2억 6,500만원
84B      전용 84.99㎡     2억 7,100만원

같은 시군구 아파트 매매 중위가(최근 12개월)   2억 3,000만원
                                       거래 1,284건

※ 분양가는 공급면적 기준, 실거래는 전용면적 기준입니다. 면적 기준이 달라
  면적당 단가는 비교하지 않았습니다.
```

공고마다 주택형·분양가·지역이 다르므로 5,911건이 전부 다른 표가 된다.

### 5.2 단가를 비교하지 않는 이유

`Transaction.exclusiveArea`는 **전용면적**이다. `SubscriptionUnit.area`는 그렇게 단순하지 않다.

어댑터가 `area: num(row.SUPLY_AR) ?? num(row.EXCLUSE_AR)`로 채우기 때문에 **행마다 기준이 다르다.**
실측(25,255 units):

| rawJson 보유 키 | units | `area`의 실제 의미 |
|---|---|---|
| `SUPLY_AR` 있음 | 20,156 (79.8%) | 공급면적 |
| `EXCLUSE_AR`만 있음 | 3,107 (12.3%) | **전용면적** |
| 둘 다 없음 | 1,992 (7.9%) | `area`가 NULL |

`houseType` `59A-1`의 `area`가 82.86㎡인 것은 공급면적이 맞지만, `84%` 타입 평균이 95.6㎡로
공급면적치고 낮게 나오는 것은 전용면적 행이 섞여 있기 때문이다.

따라서 **면적 컬럼을 "공급면적"이라고 일괄 표기하면 12%가 거짓이 된다.**

- 면적 열의 머리글은 `면적`으로 두고, **셀마다 기준을 함께 적는다** — `공급 82.86㎡` / `전용 59.99㎡`
- 기준은 렌더 시 `rawJson`에서 판정한다(`SUPLY_AR` 키가 있으면 공급, 없고 `EXCLUSE_AR`만 있으면 전용). 마이그레이션은 필요 없다
- `area`가 NULL인 행은 면적 칸을 `-`로 둔다

그리고 어느 기준이든 **면적당 단가는 비교하지 않는다.** 공급면적으로 나눈 값과 전용면적으로 나눈
값을 한 표에 섞으면 행끼리도 비교가 안 된다. **총액끼리만 비교한다** — 분양 최고가(총액)와
지역 실거래 중위가(총액)는 같은 축이다.

### 5.3 지역 매칭

**`regionCode`로는 시군구를 얻을 수 없다.** 실측: `SubscriptionNotice.regionCode`는 청약홈 자체
3자리 **시도** 코드이고(100=서울, 410=경기, 400=인천), `regionName`도 시도명뿐이다.
`Region.code`(10자리 법정동 코드)와는 **매칭이 0건**이다.

시군구는 `address` 문자열에만 있다. 그래서 **주소 앞 두 토큰으로 `Region`을 조인해 시군구를 얻는다.**

```
address "서울특별시 강동구 고덕로 399"
  → 토큰 ["서울특별시", "강동구"]
  → Region WHERE sido='서울특별시' AND sigungu='강동구' → sigunguCode '11740'
```

실측 성공률 **5,587 / 5,911 (94.5%)**. 실패 324건은 세종(시군구 계층 없음)과 일반구를 둔 시
(주소는 `경기도 수원시 …`인데 `Region.sigungu`는 `수원시 영통구`)가 대부분이다.

시군구를 못 얻거나, 그 시군구의 최근 12개월 아파트 매매가 표본 하한(30건)에 못 미치면
**비교 줄을 렌더하지 않는다.** 분양가 표만 남는다. 스냅샷 대상 시군구는 실측 249곳이다.

시군구를 새 컬럼으로 저장하지 않는다 — 마이그레이션 없이 렌더 시 `Region` 조회 한 번으로 끝난다.

### 5.4 비용

`Transaction`은 7.6M행이다. 요청 경로에서 시군구별 중위가를 매번 계산하지 않는다.
**시군구별 중위가·거래건수를 스냅샷 한 건으로 사전계산한다** — `DashboardSnapshot`에
`subscription_sigungu_median` 키로 `{ [sigunguCode]: { median, count } }` 형태를 저장한다.

`lib/guide/data-snapshot.ts`를 재사용하지 않는다. 그쪽은 키를 `guide_` 접두사로 만들고
`HeavyBlockKey` 타입에 묶여 있어 청약 키가 들어가지 않는다. 청약 전용 모듈
`lib/subscription/median-snapshot.ts`를 따로 두고, 같은 `DashboardSnapshot` 테이블만 공유한다.

갱신은 `scripts/subscription/refresh-median-snapshot.ts`가 맡고, `deploy/run-etl.sh`의
`transactions-daily`에 한 줄 추가한다(가이드 스냅샷 갱신 바로 다음). 페이지는 스냅샷에서
자기 시군구 한 줄만 읽는다.

## 6. 3단계 — 축소와 changefreq

### 6.1 410 대상

**1단계까지 마치고도 `location IS NULL`인 공고.** 지금 알 수 있는 상한은 주소가 없는 3건이고,
실제 수는 1단계의 지오코딩·검증 실패분으로 정해진다. 적용 전에 목록을 사람이 검토한다.

410 구현은 D1·D2b와 같은 방식을 따른다 — 라우트에서 410을 반환하고 사이트맵에서 뺀다.

### 6.2 changeFrequency

`lib/sitemap/sources.ts`의 subscription 소스가 5,911건 전부에 `daily`를 붙인다.
99.6%가 마감된 공고인데 매일 크롤하라고 신고하는 셈이다.

- 접수 마감(`receiptEnd < 오늘`) → `yearly`
- 진행중·예정 → `daily` 유지

## 7. 오류 처리

| 상황 | 동작 |
|---|---|
| 지오코딩 실패(응답 없음) | `location`을 채우지 않는다. 실패로 집계 |
| 지오코딩 결과가 `regionName`과 불일치 | **버린다.** 틀린 좌표는 빈 값보다 나쁘다 |
| 카카오 API 오류·한도 초과 | 그 건만 실패로 집계하고 계속 진행. 전량 실패 시 종료 코드 1 |
| 스냅샷 없음 / 시군구 매칭 실패 | 비교 줄만 빠지고 분양가 표는 남는다 |
| 시군구 표본 30건 미만 | 비교 줄을 렌더하지 않는다 |

## 8. 테스트

**유닛**
- 좌표 검증: `regionName`과 카카오 `region1/region2`가 일치·불일치일 때의 판정
- 분양가 표: units가 없을 때 `null`, `topAmount`가 없는 unit은 제외
- 시군구 중위가 조회: 스냅샷 없음 / 표본 부족 시 `null`
- changefreq: 마감·진행중 각각의 값

**통합·e2e**
- 위치 있는 공고: 지도·주변 단지·분양가 비교가 렌더된다
- 위치 없는 공고: 분양가 표는 있고 지도 블록은 없다
- 410 대상: 상태 코드 410, 사이트맵 미등재

**검증 순서**: `pnpm lint` → `typecheck` → `test:unit` → `build` → `seed:e2e` → Playwright 전량.

S-1과 S-2는 병렬 가능하다. S-3은 반드시 마지막이다.
