# ISR 캐시 축출 설계 — 컨테이너 파괴에서 선택적 삭제로

**작성일:** 2026-08-27
**배경:** 루트 디스크가 매일 70%→86%를 반복하고, 회수 수단이 web 컨테이너 재생성뿐이라 그때마다 502가 발생한다. 2026-07-25 100% 포화 사고(`docs/superpowers/plans/2026-07-21-oci-migration.md` 후속)의 미해결 잔여.

---

## 1. 문제

Next.js ISR 파일 캐시(`.next/server/app`)가 **축출 없이 무한히 증가한다.**

`revalidate`는 신선도(stale 판정) 기준이지 보존 정책이 아니다. 만료돼도 파일은 지워지지 않는다. Next 15 파일시스템 캐시에는 LRU가 없고, `next.config.mjs`에 `cacheHandler`도 설정돼 있지 않다(`output: 'standalone'`만).

그래서 유일한 회수 수단이 컨테이너 파괴(`docker compose up --force-recreate web`)였다. 이것이 502의 출처다.

### 1.1 실측 (2026-08-27, 운영 박스)

컨테이너 기동 `2026-08-26T19:00:34Z` 기준 약 12시간 경과 시점.

| | |
|---|---:|
| web 컨테이너 쓰기 레이어 | 14.8GB |
| `/app/.next/server/app` | 14GB |
| `/app/.next/cache` | 5.9MB |
| `.html` / `.rsc` / `.meta` | 63,444 / 63,444 / 66,662 |
| 페이지당 평균 | ≈235KB |

**시간당 증가율** (mtime 히스토그램 — 24시간 대기 없이 소급 측정):

```
평균 5,287 html/시간 = 1.24 GB/시간, 12시간 연속 감속 없음
```

### 1.2 정상 상태에 도달하지 못하는 구조

```
전 표면 831,513 ÷ 5,287/시간 = 157시간(6.5일)에 한 바퀴
주력 revalidate = 86,400초(24시간)

```

디스크 45GB로는 전 표면(831,513 × 235KB ≈ 195GB)을 담을 수 없다. 표면을 줄이지 않는 한 상한이 필요하다.

## 2. 기존 판단의 교정

`deploy/maintenance.sh:5` 주석은 이렇게 적혀 있다.

> `.next/server/app`: ISR 전체경로 캐시(.html/.rsc/.meta). **실행 컨테이너에서 안전삭제 불가** → 이미지에서 재생성(recreate)

**이 판단은 틀렸다.** 2026-08-27 실측으로 반증했다.

### 2.1 빌드 산출물과 런타임 생성물은 mtime으로 완전히 갈린다

| | 파일 수 | 예시 |
|---|---:|---|
| 기동 시각 **이전** = 빌드 산출물 | 325 | `privacy.html`, `_not-found.meta`, `sitemaps/[id]/route.js` |
| 기동 시각 **이후** = 런타임 ISR | 200,780 | `amenity/cafe/172547.html` |

동적 상세 라우트는 `generateStaticParams()`가 빈 배열이라 빌드 시 프리렌더되지 않는다. 따라서 상세 페이지 캐시는 **전부** 런타임 생성물이고, 기동 시각 필터로 빌드 산출물을 완벽히 보호할 수 있다.

### 2.2 실행 중 삭제가 안전하다

`/amenity/cafe/172547`의 `.html`·`.rsc`·`.meta` 3종을 삭제하고 즉시 요청:

```
before status 200
cache files removed
after  status 200 in 53ms
```

에러 없이 200을 반환했다. 응답 시간도 53ms로, 컨테이너 재생성 시의 수초 502와 비교할 수 없이 낫다.

### 2.3 atime은 추적되지만 **엄밀한 LRU는 아니다**

```
atime: 2026-08-27 00:04:25
mtime: 2026-08-26 19:00:37
```

약 5시간 간격이 기록돼 있고, atime 분포도 시간대별로 갈린다(23시 5,681 / 00시 6,290 / … / 06시 7,524). 정렬 기준으로 쓸 수 있다.

**다만 루트가 `relatime`으로 마운트돼 있다**(`findmnt -no OPTIONS /` 실측). relatime은 이전 atime이 mtime보다 오래됐거나 24시간이 지났을 때만 atime을 갱신한다. 따라서 여기서 읽히는 atime은 사실상 **"생성 후 첫 접근 시각"**이고, 그 뒤 24시간 안의 재접근은 반영되지 않는다.

즉 이 정렬은 **엄밀한 LRU가 아니라 사실상 FIFO에 가깝다.** 자주 조회되는 페이지가 보호된다고 단정할 수 없다.

**그래도 채택한다.** 근거:

- 유입의 대부분이 크롤러다(5,287페이지/시간이 12시간 연속, 사람 트래픽의 패턴이 아니다). 크롤러가 만든 항목은 사람이 다시 읽지 않으므로 LRU와 FIFO의 차이가 실질적으로 작다
- 목표는 "핫 페이지 보호"가 아니라 **"총량 상한"**이다. FIFO로도 달성된다
- 엄밀한 LRU를 얻으려면 `strictatime` 재마운트가 필요한데, 읽기마다 쓰기 I/O가 발생한다. 디스크가 압박받는 박스에서는 역효과다

잘못 축출된 핫 페이지는 다음 요청에서 재생성된다(실측 53ms). 정확성 문제는 없고 약간의 재생성 비용만 든다.

## 3. 설계

`deploy/maintenance.sh`에 ISR 선택적 축출을 추가하고, 회수 수단으로서의 `recreate_web()` 의존을 없앤다. **앱 코드는 변경하지 않는다.**

### 3.1 축출 규칙

```
1. 기준선  = 컨테이너 StartedAt (docker inspect)
2. 대상    = /app/.next/server/app 아래 기준선 이후 mtime 파일만
3. 정렬    = atime 오름차순 (§2.3 — 사실상 FIFO)
4. 단위    = 페이지 단위로 .html·.rsc·.meta 3종을 함께 삭제
5. 종료    = ISR 총량이 상한(ISR_MAX_GB, 기본 8) 아래로 내려가면 중단
```

4번이 중요하다. 파일 단위로 지우면 `.html`만 사라지고 `.meta`가 남는 부분 삭제가 생길 수 있다. `.html` 기준으로 basename을 뽑아 3종을 함께 지운다.

**총량 측정 비용.** `du -sm`은 20만 파일 순회라 수초가 걸린다. 매시간 guard에서 도는 것을 감안해 허용 범위로 보되, 실행 시간을 로그에 남겨 추적한다. 축출이 필요 없는 회차에서도 측정은 해야 하므로 이 비용은 상시 발생한다.

**기준선 확보 실패 시.** `docker inspect`가 StartedAt을 주지 못하면 축출을 건너뛰고 경고를 남긴다. 기준선 없이 삭제하면 빌드 산출물 325개가 위험하므로, 모르면 아무것도 지우지 않는다.

### 3.2 호출 지점

| 모드 | 현재 | 변경 후 |
|---|---|---|
| `guard` (매시간) | 80% 이상이면 `cleanup_safe` → 90% 이상이면 `recreate_web` | `cleanup_safe`에 ISR 축출 추가. `recreate_web`은 축출 후에도 임계 초과일 때만 |
| `weekly` | `cleanup_safe` → 60% 이상이면 무조건 `recreate_web` | 축출로 대체. `recreate_web` 호출 제거 |

`weekly`의 무조건 recreate가 매주 502를 만들던 지점이다. 축출이 같은 공간을 되찾으므로 제거한다.

### 3.3 파라미터

| 이름 | 기본값 | 근거 |
|---|---:|---|
| `ISR_MAX_GB` | 8 | 현재 총 사용 29GB − ISR 14.6GB = **기타 ≈14.4GB**(이미지 2.9 + build cache 3.8 + DB·OS 등). 여기에 ISR 8GB를 더하면 22.4GB ≈ 디스크 **50%**. 1.24GB/시간 유입을 매시간 축출로 흡수한다 |
| `GUARD_WARN` | 80 (유지) | |
| `GUARD_CRIT` | 90 (유지) | 축출 실패 시의 최후수단으로만 남긴다 |

### 3.4 관측성

8/23 사고에서 로그가 `recreate FAILED` 한 줄뿐이라 원인을 알 수 없었다. 축출 결과를 수치로 남긴다.

```
[maint] isr prune: 14.6GB → 8.0GB (6.6GB 회수, 28,100 페이지 삭제, 1,240ms)
[maint] isr prune: 상한 미만 — 건너뜀 (7.2GB / 8GB)
```

회수량 0이 반복되면 그 자체가 이상 신호로 읽힌다.

## 4. 검증

| # | 무엇을 | 어떻게 |
|---|---|---|
| V1 | 빌드 산출물 미삭제 | 축출 전후 기동 시각 이전 mtime 파일 수가 325로 동일 |
| V2 | 부분 삭제 없음 | 축출 후 `.html` 수 == `.rsc` 수 |
| V3 | 사이트 정상 | 축출 직후 `/`·`/apt/{id}`·`/amenity/cafe/{id}` 200 |
| V4 | 상한 준수 | 축출 후 ISR 총량 ≤ `ISR_MAX_GB` |
| V5 | 502 부재 | 축출 실행 중 컨테이너 재시작 로그 없음 |
| V6 | 안정성 | 2~3일간 디스크가 상한 근처에서 유지되고 `recreate` 미발생 |

V6이 애드센스 재신청의 선행 조건이다 — 서버 불안정을 제거한 상태에서 콘텐츠 심사만 받기 위해서다.

## 5. 범위 밖

| 항목 | 이유 |
|---|---|
| **공공 레지스트리 상세 549,574개 de-publish** | 캐시 상한이 생기면 디스크 근거가 사라진다. 애드센스 근거는 가설이고 미검증이다. 한 번에 한 변수만 바꿔 원인을 특정한다 |
| **매물 27만 밀도 게이트(D2b) 폐기** | 부동산은 압박의 26%에 불과했다. 표면 크기 문제를 캐시 상한으로 푸는 이상 매물을 줄일 근거가 없다. 2026-08-09 계획의 D2b는 이 문서로 폐기한다 |
| **Next `cacheHandler` 도입** | 축출을 스크립트로 해결할 수 있음이 실측으로 확인됐다. 앱 코드 변경·standalone 트레이싱·동시성 처리를 감수할 이유가 없다. 축출로 부족하다는 증거가 나오면 재검토 |
| **long-tail 동적 렌더링** | 무엇이 인기 페이지인지 판정할 데이터가 없다(GSC 서비스계정 키 미배치). 2코어 박스에 SSR 부하를 옮기는 것도 별도 위험 |
| **build cache 정리 자동화** | 이미 `cleanup_safe`에 `docker builder prune --max-used-space=3GB`로 존재한다 |

## 6. 미해결 · 후속

- **GSC 서비스계정 키 배치.** 크롤 응답코드 이력을 볼 수 있는 유일한 경로다. 심사 창의 5xx 여부를 소급 확인하려면 필요하다
- **봇 액세스 로깅.** cloudflared 로그는 user-agent를 남기지 않아 `Mediapartners-Google` 응답을 볼 수 없다. 다음 신청을 계측 가능하게 하려면 별건으로 필요하다
- **`/etc/docker/daemon.json` 형상관리.** 로그 로테이션 설정이 박스에만 존재해 재생성 시 사라진다
