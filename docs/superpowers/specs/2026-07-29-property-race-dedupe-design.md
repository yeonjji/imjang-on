# 경합 중복 단지 병합 설계

**작성일:** 2026-07-29
**배경:** `docs/superpowers/specs/2026-07-28-facility-title-locality-suffix-design.md` §7.2에 후속으로 기록된 단지 레코드 중복

---

## 1. 문제

같은 단지가 여러 `Property` 레코드로 갈라져, 거래·통계가 나뉘고 상세 페이지가 중복 노출된다.

```
삼양비취타워  동해시 묵호진동  5개 레코드
프리가        구로구 오류동    4개 레코드
```

### 1.1 실측 규모

운영 DB 읽기전용 SSH 터널(`default_transaction_read_only=on`)로 측정. 기준은 `redirectToId IS NULL` — 실제로 렌더되는 단지다.

| | |
|---|---:|
| 전체 단지 | 275,645 |
| 중복 행 | **4,128** (1.5%) |
| 중복 그룹 | **2,028** |
| 패자 쪽에 묶인 거래 | **48,264** |

그룹 크기는 쌍 1,963 / 삼중 58 / 사중 7. 유형별로는 아파트 2,210행(1,080그룹), 다세대 889행(444그룹), 오피스텔 814행(397그룹), 연립 215행(107그룹).

거래는 승자 179,948건 : 패자 48,264건으로 갈렸다. 패자 2,100행 중 275행은 거래가 아예 없다.

키를 어떻게 잡아도 같은 수가 나온다 — 중복들은 `name`·`nameNorm`·`regionCode`·`sigunguCode`가 전부 같다. `Property.regionCode`는 `getSigunguTargets()`가 주는 시군구 코드라 동 단위가 아니라 시군구 단위인 것이 원인이다.

| 키 | 행 | 그룹 |
|---|---:|---:|
| `type + name + regionCode` | 4,128 | 2,028 |
| `type + nameNorm + regionCode` | 4,128 | 2,028 |
| `type + name + sigunguCode` | 4,128 | 2,028 |
| `type + name + address` | 4,096 | 2,012 |

### 1.2 원인 — 경합

2,028그룹 중 **2,025그룹이 10초 이내**에, 평균 id 차이 2로 생성됐다. 나머지 3그룹도 5분 이내다.

```
scripts/ingest/transactions/runner.ts

tasks:  for api → for 시군구 → for 월      ← 인접 태스크 = 같은 시군구의 연속된 달
runWithLimit(pending, 2)                    ← 그 둘이 동시에 실행된다

runOne():
  propCache = 시군구 전체 스냅샷 (시작 시 1회 로드)
  캐시 miss → findOrCreateProperty()
                findFirst → null            ← 형제 태스크가 아직 커밋 전
                create                      ← 둘 다 만든다
```

`propCache.set(key, property)`는 **한 태스크 안에서만** 재생성을 막고 태스크 사이는 못 막는다. `Property`에는 유니크 제약이 하나도 없어 DB도 막지 않는다.

### 1.3 주소가 다른 20그룹 — 경합이 우연히 옳게 동작한 경우

2,028그룹 중 20그룹만 주소가 다르다. 열어보니 **전부가 중복은 아니다.**

```
동신    금동 10        (1992, 208건)  ┐ 다른 동 · 다른 준공년
동신    수송동 904     (1991, 101건)  ┘ → 별개 건물

덕일    내덕동 499-6   (1984)  ┐ 같은 동 · 43m
덕일    내덕동 499-13  (1983)  ┘ → 같은 건물, 지번 변형
```

`propCache`의 키가 `propertyType:name`뿐이라 **매처는 같은 시군구 안 동명 건물을 한 단지로 취급한다.** 경합이 없었다면 `동신`의 거래 309건이 통째로 한 레코드에 들어갔을 것이다. 즉 이 20그룹에서 경합은 두 건물을 우연히 갈라놓았다.

> 거리 값은 근거로 쓰지 않았다 — 한 시군구 안에서 319km가 나오는 행이 있다. 지오코딩 오류다. 판단은 **동 이름과 준공년**으로 했다.

### 1.4 병합 충돌은 거의 없다

| 2,028그룹 중 | |
|---|---:|
| 주소 다름 | 20 |
| 준공년 다름 | 15 |
| 세대수 다름 | **0** |
| 시군구 다름 | **0** |
| 좌표가 일부 행에만 있음 | **0** |

## 2. 범위

**병합:** 병합 키 `(propertyType, nameNorm, regionCode, address)` 기준 **2,012그룹 / 4,096행**

**보류:** 주소가 유일해 그룹을 이루지 못하는 **32행**. 이들은 §1.3의 주소 상이 20그룹에서 갈라져 나온 것으로, 별개 건물과 지번 변형이 섞여 있어 건별 판단이 필요하다(§7.1).

> §1.1의 2,028그룹(4,128행)은 `address`를 뺀 키의 수치다. `address`를 넣으면 주소가 섞인 20그룹이 쪼개져 2,012그룹/4,096행이 남는다(§1.1 표 4행). 차이인 **32행**이 병합에서 빠지며, 이들이 §7.1의 대상이다.

**미손대:** 매처의 과잉병합(`propCache` 키가 이름뿐). 중복행이 없는 동명 건물들은 이미 한 레코드로 합쳐져 있고, 이를 가르려면 거래 재배치가 필요해 규모가 다르다(§7.2).

## 3. 세 단계로 나눈다

`deploy/remote-deploy.sh`가 web 빌드 전에 `prisma migrate deploy`를 자동 실행한다. **중복이 남은 상태로 유니크 제약을 배포하면 인덱스 생성이 실패해 배포 전체가 죽는다.** 그래서 한 PR에 담을 수 없다.

| | 내용 | 배포 후 할 일 |
|---|---|---|
| **A** | 경합 방지 (코드만) | — |
| **B** | 병합 ops 스크립트 | 운영에서 수동 실행 |
| **C** | 유니크 제약 마이그레이션 | — |

A가 먼저 나가야 병합 후 재발이 없다. C는 운영이 깨끗해진 뒤에만 안전하다.

## 4. A — 경합 방지

### 4.1 태스크 순서 반전

```
현재:  for api → for 시군구 → for 월     ← 인접 태스크가 같은 시군구
변경:  for api → for 월 → for 시군구     ← 인접 태스크가 다른 시군구
```

단지는 시군구에 종속된다(`regionCode`가 시군구 코드). 동시에 도는 두 태스크가 서로 다른 시군구면 **같은 단지를 만들 수 없다.** `sigunguIds`는 250여 개이므로 월 경계에서도 "마지막 시군구 vs 다음 달 첫 시군구"라 겹치지 않는다.

`--limit`이 자르는 단위의 의미가 "시군구 N개분"에서 "월×시군구 N개"로 바뀌지만, `doneKeys` resume이 이어주므로 여러 번 실행하면 전체가 완료되는 성질은 같다.

**한계:** 시군구가 1개뿐인 실행이나 ETL 프로세스가 둘 이상 겹치는 경우는 순서만으로 막지 못한다. 그래서 4.2와 C가 함께 필요하다.

### 4.2 `findOrCreateProperty`의 유니크 위반 재조회 — C로 옮긴다

제약이 생긴 뒤 `create`가 P2002로 실패하면 형제가 방금 만들었다는 뜻이므로, 잡아서 다시 조회해 그 행을 반환해야 한다.

당초 A에 넣으려 했으나 **C로 옮긴다.** C 이전에는 제약이 없어 이 경로가 발동하지 않는 죽은 코드이고, 이 저장소의 테스트는 로컬 실 DB를 쓰므로(`tests/ingest/property-matcher.test.ts`의 `assertLocalDatabase()`) 인덱스가 없는 상태에서는 P2002를 재현할 수단이 없다. C에서 마이그레이션과 함께 넣으면 발동도 검증도 된다.

A의 순서 반전만으로 실측된 경합(2,025그룹 전부)은 사라진다.

## 5. B — 병합

### 5.1 그룹과 생존자

그룹 키: `(propertyType, nameNorm, regionCode, address)` — 네 값이 모두 같은 행들
생존자: **최소 `id`**

먼저 생성된 레코드가 색인·외부링크를 가졌을 가능성이 높아 SEO 손실이 가장 작고, 규칙이 결정적이라 재실행해도 같은 결과가 나온다.

### 5.2 알고리즘

```
각 그룹에 대해 (트랜잭션 1개):
  1. 패자의 거래마다 rawHash를 생존자 id로 재계산
       ├ 같은 해시가 이미 있음 → 그 거래행 삭제 (진짜 중복)
       └ 없음                  → propertyId·rawHash 갱신
  2. 패자.redirectToId = 생존자.id
  3. 생존자.builtYear가 null이고 패자에 값이 있으면 보충
  4. updatePropertyAggregates([생존자.id])
```

**1단계의 해시 재계산이 이 설계의 핵심이다.**

```ts
// scripts/ingest/transactions/runner.ts
function computeHash(row, propertyId) {
  const key = JSON.stringify({ p: String(propertyId), t: dealType, d: date, a: area, f: floor, ... });
  return sha256(key);
}
```

`rawHash`는 `propertyId`를 포함하고 `@@unique([rawHash])`다. 재계산 없이 `propertyId`만 옮기면, 다음 수집 때 ETL이 생존자 id로 해시를 계산해 **같은 거래가 새 해시로 다시 삽입된다**(`createMany({ skipDuplicates })`는 해시가 다르면 중복으로 보지 않는다). 이중 계산이 조용히 누적된다.

`Transaction.regionCode`는 생존자와 패자가 동일하므로(§1.4 시군구 다름 0) 갱신하지 않는다.

**해시 입력값의 타입을 ETL과 정확히 맞춰야 한다.** `computeHash`는 `JSON.stringify`를 쓰므로 타입이 다르면 같은 값이라도 다른 해시가 나온다. 실증 확인:

| 필드 | ETL(`NormalizedTransaction`) | DB(`Transaction`) | 조치 |
|---|---|---|---|
| `exclusiveArea` | `number` → `{"a":84.9}` | `Decimal` → `{"a":"84.9"}` | **`Number()` 변환 필수** |
| `contractDate` | `Date.UTC(...)` | `@db.Date`(UTC 자정) | 그대로 (`toISOString().slice(0,10)` 일치) |
| `floor`·`dealAmount`·`deposit`·`monthlyRent` | 어댑터가 `null` 사용 | `null` | 그대로 |

`Number()`는 후행 0도 정규화한다 — `Decimal('84.00')` → `84`, ETL의 `Number('84')` → `84`로 일치한다.

**남는 위험:** 원본 API가 소수 3자리 이상을 주면 `Decimal(6,2)` 저장 시 정밀도가 깎여, 재계산 해시가 다음 수집분과 어긋나 중복이 다시 생길 수 있다. §9의 사후 검증으로 잡는다.

### 5.3 패자는 삭제하지 않는다

`redirectToId`를 세워 301로 보낸다. 상세 페이지 3종에 이미 처리가 있다.

```ts
if (property.redirectToId) permanentRedirect(`/apt/${property.redirectToId}`);
```

삭제하면 이미 색인된 URL이 404가 된다. `redirectToId`는 2026-07-01 행정구역 개편용으로 도입된 것과 같은 메커니즘이고, `scripts/ops/populate-property-redirects.ts`가 같은 모양의 선례다.

### 5.4 스크립트 형태

`scripts/ops/merge-duplicate-properties.ts`. 기본 `--dry-run`, `--apply`로만 쓴다. dry-run은 그룹별 생존자·이관 건수·삭제 건수를 파일로 출력해, 확인 후 적용할 수 있게 한다.

## 6. C — 유니크 제약

```sql
CREATE UNIQUE INDEX "Property_dedupe_key"
  ON "Property" ("propertyType", "nameNorm", "regionCode", "address")
  WHERE "redirectToId" IS NULL;
```

**`CONCURRENTLY`는 쓰지 않는다.** Prisma는 마이그레이션 파일을 트랜잭션으로 감싸 실행하는데 `CREATE INDEX CONCURRENTLY`는 트랜잭션 안에서 동작하지 않는다. 저장소에 선례도 없다. `Property`는 275,645행이라 일반 인덱스 생성이 수 초 안에 끝나므로, 그동안의 쓰기 잠금은 감수한다.

**`address`를 포함하는 것이 중요하다.** 빼면 주소가 다른 20그룹(§1.3)이 제약을 위반해, 보류하기로 한 과잉병합을 강제로 끌어들이게 된다. 그 20그룹에는 별개 건물이 섞여 있어 강제 병합은 데이터 손상이다.

**`WHERE "redirectToId" IS NULL` 부분 인덱스로 둔다.** 병합된 패자와 2026-07-01 개편 때 리다이렉트된 구 레코드가 제약에 걸리지 않아야 하고, 의미상으로도 유일성이 필요한 것은 살아 있는 단지뿐이다.

Prisma 스키마는 부분 유니크 인덱스를 표현하지 못하므로 raw SQL 마이그레이션으로 작성한다. `CONCURRENTLY`는 트랜잭션 밖에서만 동작하므로 마이그레이션 파일 상단에 이를 명시한다.

## 7. 후속 (이 스펙 범위 밖)

### 7.1 병합에서 남는 32행

§1.3의 주소 상이 20그룹에서, 같은 주소끼리 묶이지 못하고 홀로 남는 행들이다. 별개 건물(다른 동·다른 준공년)과 같은 건물의 지번 변형(같은 동·수십 m)이 섞여 있다. 32행이라 건별 확인이 현실적이다. 병합 대상과 분리 대상을 갈라 처리한다.

### 7.2 매처의 과잉병합

`propCache`의 키가 `propertyType:name`뿐이라 같은 시군구 안 동명 건물이 한 레코드로 합쳐진다. 중복행이 남지 않은 경우는 실측으로 드러나지 않으며, 가르려면 거래를 주소 기준으로 재배치해야 한다. 규모 미측정.

### 7.3 좌표 오류

§1.3 측정 중 한 시군구 안에서 319km 떨어진 좌표가 관측됐다. `scripts/ops/regeocode-suspect-properties.ts`가 있으나 이 현상을 잡는지는 확인하지 않았다.

## 8. 테스트

- **태스크 순서** 단위 — 생성된 태스크 목록에서 인접 쌍이 같은 시군구를 갖지 않는다
- **병합 알고리즘** 단위 — 해시 충돌 시 삭제 / 비충돌 시 이관, 생존자 = 최소 id, `builtYear` 보충
- **통합** — 중복 쌍을 시드해 병합 후 거래 합계·`redirectToId`·집계값을 검증
- **`findOrCreateProperty` P2002 재조회** 단위

통합 테스트는 자체 시드를 쓴다 — CI의 check 잡은 시드를 돌리지 않으므로 앰비언트 데이터에 의존하면 깨진다.

## 9. 배포와 되돌리기

**A** — 코드만. revert로 끝난다.

**B** — `--dry-run` 출력을 확인한 뒤 `--apply`. `redirectToId`가 남아 어느 행이 어디로 갔는지는 추적할 수 있지만 거래 이관 자체는 되돌리기 어렵다. 실행 전 `Transaction`·`Property` 백업을 남긴다.

**B 사후 검증 (필수).** 병합 직후 생존자들의 거래 건수를 기록해 두고, 다음 daily ETL이 한 바퀴 돈 뒤 같은 수치를 다시 잰다. 늘었다면 §5.2에 적은 정밀도 문제로 해시가 어긋나 중복이 재삽입된 것이므로, 재계산 로직을 고치고 늘어난 행을 정리한다.

**C** — `DROP INDEX "Property_dedupe_key"`.

B는 운영 DB에 쓰기를 하므로 읽기전용 터널이 아닌 별도 접속이 필요하다. 실행 시점과 결과를 기록한다.
