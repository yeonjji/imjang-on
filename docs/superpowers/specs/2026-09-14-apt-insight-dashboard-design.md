# 아파트 「한눈에 보기」 대시보드 설계

**상태:** 설계 확정 대기 · 구현 착수 전
**범위:** 아파트 상세(`/apt/[id]`) 한 종류. 빌라·오피스텔·어린이집·병원·학교·도시생활은 이번 범위가 아니다.

## 1. 무엇을 바꾸나

지금 「한눈에 보기」는 문장 6~8줄이 세로로 쌓인 박스다. 이것을 **헤더 문장 + 배지 + 타일 + 카드**로 재구성한다. 문장을 읽지 않아도 숫자가 먼저 들어오게 하는 것이 목적이다.

바꾸는 것은 **표현 계층뿐**이다. 문장 생성은 그대로 둔다(§3).

## 2. 왜 아파트만인가 — 실측 근거

「한눈에 보기」는 7종이 공용한다. 유형별로 모듈이 몇 개 발화하는지 재봤다(각 표본 300).

| 유형 | 공개 페이지 | 산문 없음 | KPI 4칸 채움 |
|---|---:|---:|---:|
| 병원 | 79,772 | 2% | 97% |
| 어린이집 | 25,189 | 0% | 100% |
| 아파트 | 44,496 | 15% | 76% |
| 학교 | 12,567 | 20% | 69% |
| 오피스텔 | 17,481 | 46% | 41% |
| 빌라 | 213,363 | 42% | 29% |
| 도시생활 | 388,581 | — | 0% (모듈 1개) |

7종 전부에 적용하면 가중 평균 **27%**다. 빌라 21만 페이지 중 15만에 빈 카드가 깔리고, 도시생활 39만은 모듈이 `intro` 하나뿐이라 구조적으로 불가능하다. 그래서 아파트 하나로 구조를 검증한 뒤 병원·어린이집으로 넓히는 순서를 택했다(그 확장은 별도 스펙).

## 3. 절대 깨면 안 되는 계약

`narrative`는 화면 전용이 아니다.

- **`narrative.text`의 앞 150자가 메타 설명**이다 — `app/(public)/apt/[id]/page.tsx`
- **`narrative.fired.length >= 3`이 색인 여부를 결정**한다 — `lib/seo/indexable.ts`

문장 생성을 구조화 데이터로 **교체하면 둘 다 사라진다.** 현재 색인 대상 비율 87.0%(2026-09-14 실측, 표본 1,000)가 무너지고 수만 페이지의 검색 설명이 빈다.

따라서 **교체가 아니라 병행**한다. 각 모듈은 지금처럼 문장을 만들고, 동시에 그 문장을 만들기 전에 이미 계산해 둔 값을 구조화해 함께 내보낸다.

```ts
// lib/insights/shared.ts — 선택 필드 추가. 다른 6종은 설정하지 않으므로 영향 없다.
export interface Insight {
  key: string;
  text: string;                 // 기존 유지 — 메타 설명·색인이 쓴다
  display?: DisplayUnit[];      // 신규 — 화면만 쓴다. 한 모듈이 여러 개를 낼 수 있다
}

// shape이 판별자다. 'card'를 두 번 쓰면 TS가 구분하지 못하므로 칩 카드는 'chips'로 나눈다.
export type DisplayUnit =
  | { shape: 'tile';  key: string; label: string; value: string; sub?: string; tone?: 'up' | 'down' }
  | { shape: 'chips'; key: string; label: string; chips: { label: string; value: string }[] }
  | { shape: 'card';  key: string; label: string; value: string; sub?: string }
  | { shape: 'alert'; key: string; label: string; value: string; sub?: string };

export interface Narrative {
  sentences: string[];
  text: string;
  fired: string[];
  display?: DisplayUnit[];      // 발화한 모듈의 display를 순서대로 이어 붙인 것
  badges?: string[];
}
```

**`fired`의 구성은 바뀌지 않는다.** `display`는 `fired`에 영향을 주지 않는다. 단지정보 모듈(`unitMix`·`parking`)이 `sentences`에만 들어가고 `fired`에는 안 들어가는 기존 규칙도 그대로다.

### 값·단위는 모듈이 확정한다

`DisplayUnit.value`·`sub`는 **모듈이 완성된 문자열로 넣는다.** 화면은 파싱하거나 재계산하지 않는다.

이 규칙이 있는 이유가 있다. 초안 목업에서 「가격 흐름」 보조 문구가 `최근 실거래 29건`으로 적혀 있었는데, 원문은 `표본 93건, 최근 실거래 29억`이었다. **29억은 금액이고 건수는 93건**이다. 카드로 쪼개는 과정에서 단위가 바뀌었다. 화면이 값을 만들면 이런 오독이 배포된다.

## 4. 화면 구성

```

  [역세권] [중소형 중심]                                 ← 배지, 없으면 줄 자체가 사라짐

  ┌──────────┬──────────┬──────────┐
  │ 가격 수준 │ 가격 흐름 │ 입지      │                  ← 타일 2~3칸, 폭 균등 분배
  │ 29억     │ +17%     │ 도보 6분  │
  │송파구 13.4억│직전 12개월 대비│8호선 송파역│
  └──────────┴──────────┴──────────┘

  ┌───────────────────────────────┐
  │ 생활 편의                       │                   ← 카드, 있는 것만 쌓임
  │ 마트 1 · 카페 7 · 병원 12+ …    │
  ├───────────────────────────────┤
  │ 층별 시세   한 층당 +1%          │
  │ 최근 매매 77건 · 설명력 R² 0.35  │
  ├───────────────────────────────┤
  │ ⚠ 거래 특이사항                 │                   ← 주의 박스
  │ ±10% 이탈 4건 · 최근 1년        │
```

### 모듈 → 표시 단위 대응

| 모듈 | 보유율 | 표시 단위 | 값 | 보조 |
|---|---:|---|---|---|
| `bScale` | 88% | 헤더 문장 | `sentences[0]` | — |
| `pPeer` | 88% | 타일 `가격 수준` | `29억` | `송파구 평균 13.4억` |
| `tTrend` | 79% | 타일 `가격 흐름` | `+17%` / `−3%` | `직전 12개월 대비 · 표본 93건` |
| `aAccess` | 60% | 타일 `입지` | `도보 6분` | `8호선 송파역` |
| `aAccess` | 86% | 카드 `생활 편의` | 칩 목록 | — |
| `floorPremiumInsight` | 10% | 카드 `층별 시세` | `한 층당 +1%` | `최근 매매 77건 · 설명력 R² 0.35` |
| `flagsInsight` | 35% | 주의 박스 `거래 특이사항` | `±10% 이탈 4건` | `최근 1년` |
| `unitMixInsight` | 28% | **없음** | — | — |
| `parkingInsight` | 25% | **없음** | — | — |

`aAccess`는 역과 인프라를 한 문장에 담고 있어 표시 단위 둘을 낸다. 역이 없으면 타일만 빠지고 카드는 남는다.

**단지 구성과 주차는 표시 단위를 내지 않는다.** 같은 값이 아래 「단지 정보」 섹션과 「면적별 실거래 비교」 구성 줄에 이미 있다. 한 페이지에 세대당 주차가 두 번, 면적 구성이 두 번 나오는 것은 정보가 아니라 중복이다.

### 배지

| 배지 | 조건 | 붙는 비율 |
|---|---|---:|
| 역세권 | 최근접 역 도보 15분 이내 | 45% |
| 중소형 중심 | `unitMix.smallMidPct >= 80` | 23% |
| 대단지 | `households >= 1000` | 3% |

셋 다 붙는 경우는 드물다. 보통 0~1개이고, 0개면 배지 줄이 렌더되지 않는다. 대단지가 3%인 것은 기준이 높아서가 아니라 세대수 자체가 단지정보 매칭된 27%에만 있기 때문이다.

### 상승·하락 표기

기존 `InsightSection`이 쓰던 한국 관례를 유지한다 — **상승 빨강, 하락 파랑**. 실측 표본에서 하락이 흔하므로(`−3%`, `−9%`) 상승 전용으로 설계하지 않는다. 색에만 의존하지 않도록 부호(`+`/`−`)를 함께 표기한다(WCAG 2.1 AA).

## 5. 결측 처리

- 값이 없는 표시 단위는 **렌더하지 않는다.** 빈 타일·`정보 없음`·`—`를 두지 않는다.
- 보조 줄만 없으면 큰 숫자만 남긴다. 단지정보가 없는 전형 아파트는 `2005년`만 뜨고 세대수 줄이 빠진다.
- 타일이 0개면 타일 행이 사라진다. 카드가 0개면 카드 영역이 사라진다.
- **산문 자체가 없는 12%는 섹션 전체가 사라진다.** 현재 `InsightSection`이 `sentences.length === 0`에 `null`을 반환하는 동작을 그대로 둔다.

### 타일 개수 분포 (조합 실측에서 유도)

```
3칸  약 50%
2칸  약 25%   입지가 빠지거나(40%) 가격 흐름이 빠짐(21%)
1칸  약 5%
0칸    12%   산문 없음
```

고정 4열 그리드를 쓰면 3칸일 때 오른쪽이 빈다. **폭 균등 분배**로 2칸은 절반씩, 3칸은 3등분이 되게 한다. 모바일은 2열.

## 6. 검증

- **색인 계약 회귀 테스트** — `display`를 넣기 전후로 `fired`가 동일한지 단언한다. 기존 `tests/lib/apt-complex-narrative.test.ts:68`이 쓰는 패턴(`withMix.fired === without.fired`)을 따른다.
- **메타 설명 불변** — `narrative.text.slice(0,150)`이 변경 전후 동일한지 단언한다.
- **값 확정 규칙** — 각 모듈 테스트에서 `display[].value`가 문장 속 수치와 같은 단위인지 단언한다. 특히 `tTrend`는 `표본 건수`와 `실거래 금액`을 서로 바꿔 넣지 않았는지 본다.
- **SSR 계약** — `renderToStaticMarkup`으로 타일 0·1·2·3칸, 카드 0개, 배지 0개 각 경우를 렌더해 빈 껍데기가 남지 않는지 확인한다. 이 저장소에는 `@testing-library`가 없다.
- **배포 후 실측** — 색인 대상 비율이 87.0%에서 유지되는지 `scripts/ops/measure-narrative-index.ts`로 확인한다.

## 7. 하지 않는 것

- 문장 생성 로직·문구를 바꾸지 않는다. 이번 작업은 표현 계층이다.
- `lib/seo/indexable.ts`를 수정하지 않는다.
- 빌라·오피스텔·어린이집·병원·학교·도시생활 화면을 바꾸지 않는다. `InsightSection`은 그 6종이 계속 쓰므로 **아파트 전용 컴포넌트를 새로 만들고 기존 컴포넌트는 건드리지 않는다.**
- 「단지 정보」 섹션과 「면적별 실거래 비교」를 바꾸지 않는다.
- 새 데이터를 수집하지 않는다. 모든 값은 이미 모듈이 계산하고 있는 것이다.
