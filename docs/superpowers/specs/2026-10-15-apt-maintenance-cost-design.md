## 1. 표본 실측 (2026-10-15)

- 표본: K-apt 단지 목록(22,331개)에서 무작위로 고른 100개 단지
- 범위: 31개 오퍼레이션 × 2개월(2025-09, 2026-01) + 기본정보(`getAphusBassInfoV5`)
- 결과: 호출 오류 0건. 기본정보만 동시 6건 호출 때 HTTP 429가 났고, 순차 재시도로 전량 받았다.

| 항목 | 결과 | 설계에 주는 영향 |
|---|---|---|
| 최신 데이터 월 | **2026-08분** (2026-09·10분은 아직 응답 없음). 약 2개월 지연 | 기준 연월을 반드시 표시 |
| 단지별 응답 | 월마다 단지의 1~3%는 31개 항목이 모두 비어 있다 | 그 달 섹션 숨김 |
| 값 타입 | int · 문자열("0") · float · null이 섞여 있다 | 수집 시 숫자로 정규화 |
| 금액 단위 | 공용관리비 세대당 중앙값 약 99,000원, ㎡당 중앙값 약 1,070원(p10 약 780 ~ p90 약 1,580) | **단지 월 총액(원)** 으로 확정 |
| 관리비부과면적 `kaptMarea` | 100/100 채워짐 | ㎡당 계산 가능. 이미 `AptComplex.rawJson`에 저장된 기본정보 응답에서 읽는다 |
| 난방비 vs 난방 방식(2026-01) | 개별난방 66곳 중 64곳이 난방비 **0**(빈 값 아님). 지역·중앙난방 32곳은 전부 0보다 큼 | 검토 ① 확인. 총액·개별사용료로는 단지 간 비교를 하지 않는다 |
| 전기료 전용분 `electP` | 13%가 0 | 한전 직접 계약으로 추정. 개별사용료 비교 제외 근거 |
| 계절 차이 | 난방 전용분이 0보다 큰 단지: 9월 8곳 → 1월 32곳 | 겨울·여름 비교 가능(지역·중앙난방 단지만 의미 있음) |
| 0 vs 빈 값 | 대부분의 항목에서 0이 흔하다(차량유지비 95% 이상, 안전점검비 약 75%) | 0은 0으로 합산하고, 항목 줄에서는 0인 항목을 숨긴다 |

**명세와 실제가 다른 곳:** 개별사용료 API는 Swagger 명세에 오퍼레이션명이 `...InfoV2`로 적혀 있지만, 실제로는 `...InfoV3`여야 호출된다(V2는 `NO_OPENAPI_SERVICE_ERROR`). 정화조오물수수료만 명세에도 V3로 적혀 있다.

## 2. 호출량과 수집 전략

- 단지 하나의 한 달치를 받는 데 31번 호출한다.
- 22,331개 단지 기준으로 API별 월 호출량은 다음과 같다.
  - 공용관리비: 17 × 22,331 ≈ 38만
  - 개별사용료: 10 × 22,331 ≈ 22만
  - 장기수선충당금: 4 × 22,331 ≈ 9만
- 개발계정 한도는 API당 하루 5,000번, 한 달 약 15만 번이다. 공용관리비는 개발계정으로 한 달치를 다 받을 수 없다.

**결정: A안 + 점진 수집**
1. **운영계정 트래픽 증설을 신청한다(사용자).** 3개 API 모두, 활용사례에 imjangon.co.kr을 등록한다.
2. 증설 전에는 개발계정 한도 안에서 **시군구 순서로 점진 수집**한다. 하루에 약 290개 단지(공용 5,000 ÷ 17)씩 진행된다.
3. **수집 범위는 '최신 월' 하나로 시작한다.** 과거 12개월을 한꺼번에 받지 않는다. 추이는 매달 쌓이면서 생긴다. 겨울 비교용으로 직전 1월분만 추가로 받는다.
4. 증설이 승인되면 같은 스크립트가 하루에 더 많이 진행할 뿐이고, 코드는 바꾸지 않는다.

## 3. 데이터 모델

```prisma
/// K-apt 관리비. 단지 × 부과연월 한 행. 금액 단위는 원(단지 월 총액).
model AptMaintenanceCost {
  kaptCode  String @db.VarChar(20)
  yearMonth String @db.Char(6)          // 'YYYYMM' 부과연월

  // 공용관리비 (표시 묶음)
  labor        BigInt?  // 인건비 9필드 합
  cleaning     BigInt?
  guard        BigInt?
  disinfection BigInt?
  elevator     BigInt?
  homeNetwork  BigInt?
  consignFee   BigInt?  // 위탁관리수수료
  repairs      BigInt?  // 수선비 + 시설유지비 + 안전점검비 + 재해예방비
  commonEtc    BigInt?  // 제세공과·차량·사무·피복·교육·기타부대비용 합
  commonTotal  BigInt?  // 공용 17개 오퍼레이션 전체 합 (㎡당 비교의 분자)

  // 개별사용료 (해당 단지 안에서만 표시, 단지 간 비교 안 함)
  heat        BigInt?   // 전용 + 공용
  hotWater    BigInt?
  gas         BigInt?
  electricity BigInt?
  water       BigInt?
  individualEtc BigInt? // 생활폐기물·입대의·건물보험·선관위·정화조 합

  // 장기수선충당금 (원값 그대로, 평가하지 않음)
  ltrLevy    BigInt?             // 월부과액
  ltrUse     BigInt?             // 월사용액
  ltrBalance BigInt?             // 충당금 잔액
  ltrRate    Decimal? @db.Decimal(6, 2) // 적립요율(%)

  /// 31개 오퍼레이션이 모두 정상 응답했는지. false면 화면에 쓰지 않는다(한도 초과로 중간에 끊긴 행).
  complete  Boolean
  raw       Json      // 오퍼레이션별 원 응답 item. 감사·재계산용
  fetchedAt DateTime  // 조회 시점(화면에 표시)

  @@id([kaptCode, yearMonth])
  @@index([yearMonth])
}

/// 시군구 × 월 공용관리비 ㎡당 중앙값. ETL이 수집 직후 계산해 저장한다(화면은 읽기만).
model AptMaintenanceCostStat {
  sigunguCode String @db.VarChar(5)
  yearMonth   String @db.Char(6)
  medianCommonPerM2 Int   // 원/㎡
  sampleCount       Int   // 계산에 쓴 complete 단지 수
  computedAt        DateTime

  @@id([sigunguCode, yearMonth])
}
```

- 마이그레이션은 이 두 테이블 추가만 한다. 기존 테이블은 바꾸지 않는다.

## 4. 수집 (ETL)

새 스크립트 `scripts/ingest/apt-maintenance-cost/`. 기존 `apt-complex` 수집의 구조(http · adapter · runner)를 따른다.

- **대상:** `AptComplex` 중 `inUse = true`이고 `propertyId`가 있는 단지. 우리 페이지가 있는 단지만 받는다. 순서는 `sigunguCode, kaptCode`.
- **월 결정:** 최신 월 = 오늘 기준 2개월 전부터 거꾸로 probe(표본 단지 3곳)해서 응답이 있는 첫 달.
- **재개:** `(kaptCode, yearMonth)` 행이 `complete = true`면 건너뛴다. 한도 초과(에러코드 22)를 만나면 그 자리에서 정상 종료한다. 다음 실행이 이어서 진행한다.
- **동시성:** 3 이하. 실측에서 동시 6건 때 429가 났다.
- **정규화:** 문자열·float·null을 숫자로 바꾼다. 빈 문자열과 null은 null, "0"은 0.
- **complete 판정:** 31개 오퍼레이션이 모두 `resultCode 00`으로 응답했는지. item이 비어 있는 정상 응답은 "그 달 미공개"로 보고 `complete = true`, 금액은 전부 null로 둔다.
- **통계:** 수집이 끝나면 그 달의 시군구별 `commonTotal ÷ kaptMarea` 중앙값을 다시 계산한다. complete이면서 금액이 있는 단지가 5개 이상인 시군구만 저장한다.
- **스케줄:** 온박스 systemd 타이머 `apt-maintenance-cost`, 매일 1회. 한도가 남아 있는 동안만 진행하고 끝나면 종료한다.
- **실행 기록:** `IngestionRun`에 source `apt-maintenance-cost`, targetKey = 연월.
- **출처 레지스트리:** `lib/data-sources.ts`에 `kapt-maintenance-cost` 추가.

## 5. 화면 로직 (UI 모양은 시안에서 확정)

- 위치: 아파트 상세 `ComplexInfoSection` 바로 아래, id `maintenance-cost`
- 데이터: 그 단지의 complete 행 중 금액이 있는 최신 월 1개 + 최근 12개월(있는 만큼)
- **숨김:** 금액이 있는 complete 행이 하나도 없으면 섹션 전체를 숨긴다.

| 블록 | 표시 조건 | 내용 |
|---|---|---|
| 요약 | 항상 | "2026년 8월 공용관리비 ㎡당 ○원" (임장ON 계산: 공용관리비 ÷ 관리비부과면적) |
| 구 비교 | 그 달 `AptMaintenanceCostStat` 존재(표본 5개 이상) | "○○구 아파트 중앙값(○개 단지)보다 ○% 높음/낮음". ±5% 안이면 "비슷함" |
| 항목별 내역 | 항상 | 공용: 인건비·청소·경비·승강기·수선·시설·위탁수수료·기타 / 개별: 난방·급탕·가스·전기·수도·기타. **0인 항목은 숨김.** 세대당 금액 병기 |
| 추이 | 금액 있는 월이 3개 이상 | 월별 공용관리비 ㎡당 |
| 겨울·여름 | 같은 연도의 1월과 7·8월 행이 모두 있고, 난방 방식이 지역·중앙난방 | "1월 난방비 ○원, 8월 ○원 (지역난방)". 개별난방 단지는 "개별난방: 난방비가 관리비에 포함되지 않습니다" 한 줄 |
| 장기수선충당금 | `ltrLevy` 또는 `ltrBalance`에 값 | 월부과액·잔액·적립요율. 평가 문구 없음 |
| 출처 | 항상 | "국토교통부 공동주택관리정보시스템(K-apt) · 단지 관리주체 공개 자료 · 2026년 8월 부과분 · ○월 ○일 조회" |

- 세대당 금액 = 항목 ÷ `AptComplex.households`. 세대수가 없으면 세대당 금액은 생략한다.
- 난방 방식은 `AptComplex.heatType`.
- 이 섹션이 생겨도 사이드바 목차(`DetailSidebar`)에 항목을 추가하는 것 외에 기존 섹션은 건드리지 않는다.

## 6. 테스트

- **유닛:** 정규화(타입 혼합), 묶음 합산(인건비 9필드, 수선 4필드, 공용 17개 전체), complete 판정, ㎡당 계산, 중앙값(짝수·홀수·5개 미만 제외), 0 항목 숨김, 겨울·여름 표시 조건(개별난방 분기)
- **수집 통합:** 한도 초과(에러코드 22) 시 정상 종료 후 재개, 이미 complete인 행 건너뛰기. HTTP는 픽스처로 대체한다.
- **화면:** 데이터 없음 → 섹션 없음, 표본 4개 이하 → 구 비교 블록 없음, 개별난방 문구
- **e2e:** `seed-e2e.ts`에 관리비 픽스처 1단지를 추가하고 섹션 렌더 확인
- **머지 전 실데이터 QA:** 읽기전용 터널로 운영 DB 단지 5곳 확인(지역난방·개별난방·대단지·소단지·데이터 없음)
