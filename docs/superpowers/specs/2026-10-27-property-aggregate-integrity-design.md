## 1. 원천 대조 결과

### 1-1. 강남구 2026-06 아파트 매매: 원천 231 vs DB 213

건별로 다중집합 대조했다. 키는 단지명·계약일·전용면적·층·금액이다.

| 분류 | 건수 | 내용 | 원인 |
|---|---:|---|---|
| A. 같은 조건 기록 여러 건 | 10 | 원천에 같은 키가 2~3개다. **9건은 '해제된 원거래 + 같은 조건 재신고' 쌍**(예: 까치마을 06-20 34.44㎡ 6층 14.5억: 해제 08-04 + 정상 1건). 1건은 해제 없이 동일 2건(우민) | `computeHash`가 계약 정보만 써서 같은 해시가 된다. `skipDuplicates`로 1행만 남는다 |
| B. 정정 | 2 | 면적이 정정됐다(거평프리젠 30.22→30.21, 청담건영 84.6→84.59). DB에는 **이전 값 행이 남아 있다**("DB에만" 2건이 이것) | 정정 신고가 수집 창 밖에서 일어났다. 해시가 달라 창 안이었다면 **중복 행**이 생겼을 것이다 |
| C. DB에 대응 행 없음 | 8 | 등기일이 8~10월인 건 등 | 이 시군구·월 수집은 **7/31이 마지막**이다(일일 = 당월·전월). 그 뒤 원천에 추가된 신고(지연·정정 재신고)를 받지 못했다 |
| 합계 | 20 누락, 2 잔존 | 231 − 20 + 2 = 213 | |

- **해시 충돌:** 순수한 충돌(서로 다른 실제 거래가 우연히 같은 키)은 위 '우민' 1건 후보뿐이다. 나머지 A는 원천이 같은 키로 '해제본+재신고본'을 함께 공개한 결과다.
- **매칭 실패(이름 없는 행 건너뜀, `if (!row.name) continue`):** 원천 3곳 확인 결과 빈 이름 0건이다. 이번 차이의 원인이 아니다.

### 1-3. 추가로 확인된 사실
- **해제일 파싱 오류:** 저장된 `cancelDate` 32,821건이 **전부 1923~1926년**이다. 원천 형식은 `YY.MM.DD`(예: `26.09.09`)인데, `parseYmdString`은 8자리 `YYYYMMDD`를 가정해서 연도를 19YY로 만든다. 등기일자 버그와 같은 원인이다. 해제 여부(값 유무) 판단에는 영향이 없지만 날짜는 틀렸다.
- **해제일 없는 해제:** `cancelType='O'`는 35,684건인데 `cancelDate`가 있는 건 32,821건이다. 2,863건은 해제인데 해제일이 null이다. **해제일만 보는 기존 필터(가이드·청약 중앙값·이상치)는 이 2,863건을 유효 거래로 센다.**

| 원인 | 복구 |

## 2. 거래 식별 방식 변경

- **지금:** `rawHash = sha256(propertyId, 거래유형, 계약일, 면적, 층, 금액, 보증금, 월세)`, `@@unique([rawHash])`, `createMany skipDuplicates`
- **문제:**
  - 같은 키의 서로 다른 원천 기록(해제본·재신고본·동일 조건 실거래 2건)을 구분하지 못한다.
  - 해제 상태를 갱신할 수단이 없다.
- **변경:**
  1. **재정합 키** = (source, 시군구, 계약 연월) 범위 안에서 `(단지명, 계약일, 면적, 층, 금액, 보증금, 월세, 해제여부)`
     - 해제여부는 `cancelType='O'`이면 '해제', 아니면 '정상'이다.
     - 원천 레코드와 DB 행을 **키별 개수**로 맞춘다.
  2. **rawHash** = `sha256(위 재정합 키 + 순번)`. 순번은 같은 키 안에서 1, 2, …다.
     - 동일 조건 실거래 2건이 둘 다 저장되고 unique 제약도 지킨다.
     - 기존 행의 rawHash는 그대로 둔다. 재정합은 해시가 아니라 키 개수로 비교하므로 섞여도 문제없다.

## 3. 해제·정정·추가 신고 반영 = 시군구·월 재정합

### 3-1. 절차 (한 범위 = source × 시군구 × 계약 연월)
1. 원천 전 페이지를 받는다. **모든 페이지 성공 + 받은 건수 = totalCount**일 때만 다음 단계로 간다. 아니면 이 범위는 건너뛰고 ERROR로 기록한다.
2. **안전 가드:**
   - 원천 건수가 DB 건수보다 10% 넘게 적거나, 삭제 예정 행이 범위의 10%를 넘으면 반영하지 않고 경고한다(원천 일시 장애로 대량 삭제되는 것을 방지).
   - 수치는 dry-run 실측 후 확정한다.
3. 한 **DB 트랜잭션** 안에서 처리한다.
   - 범위 자문 잠금(advisory lock)을 건다. 같은 범위를 동시에 처리하지 않는다.
   - 키별로 `원천 개수 n`, `DB 개수 m`을 비교한다.
   - `n > m`: n−m개 INSERT(순번 m+1…n)
   - `m > n`: 순번이 큰 행부터 m−n개를 **`TransactionArchive`로 이동**(이유 '재정합', 시각 기록)
   - 바뀐 행의 매물 id를 **재집계 대기열**에 넣는다(§4).
   - 범위의 `IngestionRun`을 OK로 기록한다.
   - 커밋한다. 어느 단계에서 실패해도 전부 롤백되고, 다음 실행이 같은 범위를 다시 처리한다.

### 3-2. 해제 상태가 잘못 초기화되지 않는 이유
- 해제 여부가 **키의 일부**이므로 해제본과 정상본은 서로 다른 키다. 한 행의 상태를 바꾸는 갱신이 없다. 순서가 바뀌거나 재실행돼도 결과는 원천 다중집합과 같다(멱등).
  - 예: 원천에 [해제 1, 정상 1] → DB는 해제키 1행, 정상키 1행
  - 같은 범위를 몇 번 다시 돌려도 결과가 같다.
- 원천이 해제 기록을 내리면(정정 등) 그 키의 n이 줄어 행이 보관 테이블로 간다. 원천이 정답이라는 원칙을 따른다.
- **부분 실패:** 페이지 일부만 받으면 1단계에서 범위 전체를 건너뛴다. DB 쓰기 중 실패하면 트랜잭션 롤백이다. 반쯤 반영된 상태가 남지 않는다.
- **동일 범위 재수집:** 일일 수집도 같은 재정합 경로를 쓰므로 '추가만 하는' 경로가 사라진다. 같은 키 개수가 같으면 쓰기가 없다.

### 3-3. 보관 테이블과 롤백
- `TransactionArchive`: Transaction과 같은 컬럼 + `archivedAt`, `reason`, `runId`
- 되돌리기는 `runId`로 행을 Transaction에 복원하고, 그 run이 넣은 행(`createdByRunId`)을 지운 뒤 매물을 대기열에 넣는다.
  - `Transaction`에 `ingestRunId` 컬럼을 추가하는 마이그레이션이 필요하다.

### 3-4. 재정합 주기와 호출량
- **일일:** 당월·전월(지금과 같은 범위, 경로만 재정합으로)
- **추가:**
  - 주 1회 2~6개월 전
  - 월 1회 7~12개월 전
  - 결정 5: 최근 12개월 우선
- 호출량
  - 지금 일일: 6 API × 약 250 시군구 × 2개월 ≈ 3,000회/일
  - 추가: 주간 6×250×5 = 7,500회/주, 월간 6×250×6 = 9,000회/월 → 하루 평균 약 1,370회 추가. 요일·시군구를 나눠 고르게 분산한다.
  - **확인 필요:** MOLIT 개발계정 API별 일일 한도. 한도가 부족하면 매매 3종 우선(해제가 있는 API), 전월세는 월 1회로 줄인다.
- **1회 회수:** 배포 뒤 최근 12개월 재정합 1회(약 1.8만 호출, 여러 날에 분산). 그 이전 과거분은 §7에서 결정한다.

## 4. 집계 원자성·동시성 — 재집계 대기열

### 4-1. 설계
- 신규 테이블 `PropertyAggregateQueue(propertyId PK, enqueuedAt)`
- **넣기:** 거래를 바꾸는 모든 경로가 **같은 DB 트랜잭션**에서 `INSERT … ON CONFLICT (propertyId) DO UPDATE SET enqueuedAt = now()`를 한다.
  - 대상 경로: 재정합(§3), 매물 병합(`merge-duplicate-properties`), D2 창 만료 작업
  - 거래가 커밋되면 대기열 기록도 반드시 커밋된다. 프로세스가 중간에 죽어도 집계 대상이 사라지지 않는다(D1 원인 제거).
- **비우기:** 집계 작업이 묶음 단위로 처리한다.

  ```sql
  BEGIN;
  SELECT propertyId FROM "PropertyAggregateQueue" ORDER BY propertyId LIMIT 2000 FOR UPDATE SKIP LOCKED;
  -- 해당 매물 집계 UPDATE(유효 거래 기준, 값이 다를 때만)
  DELETE FROM "PropertyAggregateQueue" WHERE propertyId = ANY(:ids);
  COMMIT;
  ```

### 4-2. 정합성 검토
- **집계 도중 새 거래가 들어오는 경우:** 넣는 쪽의 `ON CONFLICT DO UPDATE`는 비우는 쪽이 `FOR UPDATE`로 잡은 행에서 대기한다. 비우는 쪽이 커밋(삭제)한 뒤 넣는 쪽 INSERT가 새 행을 만든다. 그래서 다음 묶음에서 다시 집계된다. **갱신 손실이 없다.**
- **집계끼리 동시 실행:** `SKIP LOCKED`라 같은 매물을 두 작업이 동시에 집계하지 않는다.
- **오래된 값으로 덮어쓰기:** 집계는 언제나 그 시점에 커밋된 거래 **전체**로 다시 계산한다(증분 덧셈이 아니다). 그래서 늦게 실행된 쪽이 항상 최신 상태를 쓴다.
- **완료 기록과의 관계:** 범위 OK 기록은 재정합과 같은 트랜잭션이다. 집계는 대기열이 보장하므로 OK 기록과 분리해도 누락이 없다.
- **중복 저장:** 재정합은 키 개수를 맞추는 방식이라, 재실행해도 같은 키가 두 번 들어가지 않는다. rawHash unique가 이중 안전장치다.
- **다른 수집과 동시 실행:** 범위 단위 자문 잠금(§3-1)으로 같은 범위의 재정합이 겹치지 않는다. 서로 다른 범위가 같은 매물을 바꾸는 경우(예: 매매·전세 수집)는 대기열이 합쳐 준다.

### 4-3. 실행 위치
- 대기열 비우기 작업은 수집 실행 끝과 별도 타이머 둘 다에서 호출한다(멱등).
- `install-timers.sh`의 JOBS와 `systemctl start` 목록에 둘 다 추가한다.

## 5. 유효 거래·표시 기준 (확정)

- **유효 거래(통계 대상):** `"cancelType" IS DISTINCT FROM 'O' AND "cancelDate" IS NULL`
  - 해제 구분값만 있는 2,863건도 제외된다. 공용 상수 `lib/transaction/valid-deal.ts`에 둔다.
- **통계에서 제외:** 평균, 12개월·누적 건수, 최근 매매가, 그래프, 면적별·층별·동일 조건 비교, 이상치, 색인 판정, 동네 최근 거래, 지역 통계·인기 지역·브리핑, 가이드 데이터 블록, 청약 시군구 중앙값
  - 가이드 블록과 청약 중앙값은 기존 `cancelDate IS NULL`을 이 상수로 교체한다.
- **내역 표:** 해제 거래를 남기고 **'해제' 배지**를 붙인다(`getUnifiedTransactions`, `getTransactionsByType`). 범례 문구를 추가한다.
- **`txCountTotal`:** 해제를 제외한 **유효 거래 수**로 정의한다.
- **해제일:** `YY.MM.DD`를 20YY로 해석한다. 해제일 표시는 배지 툴팁에만 쓴다.

## 8. 운영 재집계·재정합 안전 절차

### 단계 0 — 로컬 리허설(운영 영향 0)
- 운영에서 시군구 2곳(대형 1, 소형 1)의 Property·Transaction 슬라이스를 로컬 docker DB로 복사한다(읽기 전용 `\copy`, 생성열 제외, ANALYZE).

### 단계 1 — 운영 dry-run(쓰기 없음)
- 읽기 전용 세션에서 전체 매물 재집계 차이와 재정합 차이(대상 시군구·월 10개)를 계산한다. 쓰기 예정 행 수만 보고한다.
- 동시에 박스 CPU, 로드, DB 활성 세션, `pg_stat_activity` 대기, 응답 시간을 1분 간격으로 기록한다.
- **중단 기준:** 박스 CPU 80% 이상 5분 지속, 또는 사이트 응답 p95 2초 초과 → 일시정지

### 단계 2 — 운영 1묶음 적용
- 매물 2,000개(집계) 또는 시군구·월 1개(재정합)만 `--apply`
- **사전 백업:** 바뀔 행의 이전 값을 `COPY … TO` 파일로 저장한다. 재정합은 보관 테이블이 백업 역할을 한다.
- **확인 항목:**
  - 잠금: `pg_locks`에서 대기 0, 행 잠금만 있고 테이블 잠금이 없는지
  - 쓰기 행 수, WAL, 디스크(`df`), 데드 튜플(`pg_stat_user_tables`)
  - 해당 페이지 화면(로컬 읽기 전용 렌더)
- 롤백 스크립트를 실제로 1회 실행해 원상 복구를 검증한 뒤 다시 적용한다.

### 단계 3 — 10묶음 → 전체
- **시간대:** ETL 타이머와 겹치지 않는 시간에 실행한다. 실행 직전 `systemctl list-timers`와 실행 중인 잡을 확인한다. ETL과 같은 전역 자문 잠금 키를 써서 상호 배제한다.
- **속도 제한:** 동시 1, 묶음 사이 2초
- **체크포인트:** 처리한 최대 id(집계)나 범위 목록(재정합)을 파일과 IngestionRun에 기록해 언제든 중단·재개할 수 있게 한다.
- **킬 스위치:** 파일 `/tmp/reagg.stop`이 있으면 현재 묶음까지 끝내고 멈춘다.
- **디스크 가드:** 루트 여유가 10GB 미만이면 중단한다(현재 16GB).
- **잠금 영향:** UPDATE는 행 잠금만 잡고 읽기(MVCC)를 막지 않는다. 같은 매물을 바꾸는 ETL과는 자문 잠금으로 겹치지 않는다.

### 측정치 (참고)
- 2,000개 매물 묶음의 거래 조회는 인덱스만 써서 6.8만 행에 0.8초였다.

## 11. 배포·복구 계획 (S1~S3, 불일치 기간 최소화)

### 11-1. 원칙
- **S1을 단독으로 배포하지 않는다.**
  - S1은 실시간 조회만 새 기준으로 바꾼다. 그래서 재집계 전까지 같은 페이지에서 저장값과 실시간값이 갈린다.
  - 아파트 273곳은 상단 최근 매매가(해제 가격)와 그래프 최근가가 다르게 보인다. 4,444곳은 12개월 지표, 14,923곳은 누적 건수가 갈린다(2026-10-27 실측).
- **S1+S2를 한 배포 창에 함께 내고, 곧바로 해제 아파트 대상 재집계를 실행한다.** 그러면 S1 때문에 생기는 불일치 기간이 '배포 ~ 대상 재집계 완료'(수십 분)로 줄어든다.
- D1·D2(집계 누락·12개월 고정)는 S1과 무관하게 이미 있는 불일치다. S4(dry-run) → S5(전체 재집계)로 단계적으로 없앤다.
- S3(재정합)는 거래를 바꾸면 같은 트랜잭션에서 대기열에 넣는 구조다. S2가 먼저 운영 중이면 재정합분은 당일 대기열 비우기로 집계까지 반영되므로 새로운 불일치 기간을 만들지 않는다.

### 12-4. 이 리허설이 보장하지 않는 것
- **S3(재정합)는 반영되지 않았다.** 재정합이 해제·정정·추가 신고 거래를 넣고 빼면, 그만큼 추가 재집계가 생긴다. 그 성능과 변경량은 S3 리허설에서 따로 잰다.

### 13-4. 예상 운영 부하 (운영 건수 기준 추정, 리허설에서 실측)
- **기준(2026-10-28 읽기 전용 집계):** 최근 13개월 거래 222만 행(매매 3종 69만), Transaction 767만 행·4.6GB(행당 약 628B), 범위 최대 3,506행(아파트 전월세)
- **원천 호출:** 일일 그대로(6 API × 약 256 시군구 × 2개월 ≈ 3,072범위). 재확인이 하루 최대 1,550범위 더한다. API 하나에 몰려도 하루 약 2,100회(+페이지)로 개발계정 한도(API별 10,000회) 안이다.
- **첫 바퀴(배포 후 7~30일에 나눠서):** 표본 7곳의 차이율 2~12%를 적용
  - 삽입: 4.5만~27만 행 → 테이블+인덱스 약 30~170MB, WAL 약 90~540MB(재활용됨)
  - 보관: 해제 미반영분(아파트 매매 기록 6,519건 대비 원천이 약 5배)과 오피스텔·연립 매매 해제(14만 행의 2~3%) 중 재신고가 없는 것 + 정정 → 최대 약 4만 행·40MB. 같은 수의 dead tuple(autovacuum)
  - `ReconcileInsert`: 삽입 1건당 약 100B(인덱스 2개 포함) → 최대 약 27MB
- **추가 재집계:** 바뀐 매물만 대기열에 들어간다. 첫 바퀴에서 최대 약 15만 매물(최근 12개월 거래 매물 수 상한)을 7~30일에 나눠 → 하루 최대 약 2만 매물 = 2,000개 묶음 10개(S4 실측 조회 0.9초/묶음). 실제 값이 바뀌는 행은 그보다 적다. WAL은 변경 1행당 약 2.2KB → 첫 바퀴 전체 최대 약 330MB
  - S5(99,670행) 뒤에 첫 바퀴를 돌리면, S5가 고친 매물 중 S3로 거래가 바뀐 곳만 다시 계산된다(두 작업이 서로를 되돌리지 않는다. 집계는 늘 커밋된 거래 전체로 다시 계산).
- **이후 정상 상태:** 해제·정정·지연 신고만큼(월 수천 행 수준)
- **디스크:** S3가 더하는 것은 한 달에 최대 약 1GB(WAL 포함, 대부분 재활용)다. 디스크 여유가 13~16GB를 오가는 원인은 ISR 캐시 증가(시간당 1.8~2.1GB)와 매시 `isr prune`(8GB 상한)이며, 누수가 아니다.

- 남은 위험(아래 13-6)

### 13-6. 남은 위험
1. **매물 병합 도구(`merge-duplicate-properties`)**: 옛 해시로만 충돌을 본다. 생존 매물에 재정합이 넣은 같은 거래가 있으면 병합 후 중복이 되고, 재정합은 이를 orphan으로 남긴다(건수 차이로 지우지 않으므로). **`--apply`를 코드에서 차단했다**(함수 진입·CLI 모두, DB 접근 전, 종료 코드 2). dry-run은 허용. 재정합 키 기준 재작성은 별도 작업이며, 그때 건너뛴 apply 테스트 10건을 다시 켠다. 수동 실행 경로(`pnpm ops:merge-properties`)만 있고 타이머·워크플로에는 없다.
2. **가드에 걸린 범위의 새 매물**: 매물 확정이 재정합 트랜잭션 밖이라, 가드에 걸려도 새 매물 행은 생긴다(거래 0건). 기존 수집기와 같은 동작이다.
3. **원천 페이지 순서 안정성**: 같은 범위(2,092행)를 두 번 받으니 바이트 동일(2026-10-28). `numOfRows=5000` 한 번 호출로 바꿔 운영 범위(최대 3,506행)는 페이지 경계가 없다. 5,000건 초과·건수 축소 때만 페이지 수집으로 전환하며, 같은 페이지 반복은 불완전으로 본다.
4. **영구 가드 범위**: 같은 범위가 매일 가드에 걸리면 매일 경고가 나고 `--limit` 일부를 쓴다. 리허설 dry-run으로 가드 비율을 보고 기준을 확정한다.
5. **계약일 파싱 실패 행**: 어댑터가 오늘 날짜로 바꾸는 기존 동작. 이번 달 범위에 들어가 일일 수집이 넣는다(기존과 같음). 다음 달에는 범위 밖으로 빠진다.
6. **다른 범위에 재정합이 넣은 같은 거래**: 옛 해시로 저장된 행만 범위 밖 중복으로 알아챈다. 행정구역 코드가 바뀌는 동안 옛·새 코드가 모두 응답하면 두 범위에 같은 거래가 들어갈 수 있다.
7. **운영 측정 없음**: 호출량·쓰기량은 건수 기반 추정이다. 통합 리허설(운영 읽기 전용 dry-run + 로컬 적용·롤백)에서 실측한다.

### 14-3. 리허설에서 찾은 결함과 수정
- **면적 반올림 불일치로 매 실행 '정정' 왕복:** 원천 84.975는 이진수로 84.97499…라 DB에 84.97로 저장되는데, 재정합 키는 문자열 반올림으로 84.98을 만들었다. 같은 거래가 매번 정정으로 보관·재삽입됐다(156범위 재실행에서 10건).
- **수정:** 키를 실제 저장 규칙(유효숫자 16자리 → 둘째 자리 반올림)으로 만든다. 1.000~99.999 전부(99,000값)를 Prisma로 넣어 저장값과 일치함을 테스트로 고정했다. 새 행은 그 문자열로 넣어 저장값 = 키가 되게 했다(Prisma의 number 변환에 기대지 않음). 수정 후 정정 12 → 2, 재실행 변경 0.
- **매물 불일치 229건의 원인:** 원천이 단지명을 바꿨다(예: 신촌숲아이파크 → 마포아이파크포레). 옛 거래는 옛 이름 매물에, 원천은 새 이름 매물로 확정된다. '매물만 다르면 그대로' 규칙이 이 229건의 **중복 삽입을 막았다.** 단지명 변경으로 매물이 갈리는 것은 S3 이전부터 있던 문제다(추후 개선).
