# 동네 실거래 목록 — 홈 히어로 패널 + 상세 섹션 설계

**상태:** 설계 확정 대기 · 구현 착수 전
**범위:** 홈(`/`) 히어로 오른쪽 패널, 실거래가 상세(`/apt/[id]`·`/villa/[id]`·`/officetel/[id]`) 섹션 하나.

> **개정 이력**
> - 2026-09-16 초안
> - 2026-09-16 리뷰 반영 — 상세 배치를 가격 추이 아래로, 홈 왼쪽 열에 통계 배치 명시, 건물유형 필터 추가, 연도 표기, 빈 결과 처리, 조회 단계 제외, 취소 거래 제외, 임계값 근거 교정

## 1. 무엇을 만드나

한 동네의 최근 실거래를 **거래 단위**로 나열하는 목록을 두 곳에 넣는다.

- **홈** — 히어로 오른쪽에 지역·유형 선택 + 압축 목록
- **상세** — 그 매물이 속한 동의 거래 표. 지역 선택 없음

두 화면은 **조회 함수와 금액·날짜 포맷을 공유하고, 배치는 공유하지 않는다.** 좁은 홈 패널과 넓은 상세 본문은 쓸 수 있는 공간이 다르다.

## 2. 기존 「주변 단지 실거래가 비교」와의 관계

상세 하단에 이미 `NearbyPriceComparison`이 있다. 데이터는 다르지만 **사용자에게 중복으로 보이지 않게 제목으로 구분한다.**

| | 기존 | 신규 |
|---|---|---|
| 제목 | **주변 단지 가격 비교** — 가까운 순 | **{동} 최근 거래** — 계약일순 |
| 단위 | 단지 (Property 1행) | 거래 (Transaction 1행) |
| 범위 | 반경 2km (`ST_DWithin`) | 같은 읍·면·동·리 |
| 내용 | 단지별 최신 매매/전세/월세 요약 | 거래 건별 계약일·면적·가격·층 |

각 제목 아래에 정렬 기준을 부제로 적어 성격 차이를 드러낸다.

## 3. 데이터 — 실측으로 확인한 제약

### 3.1 `Transaction.regionCode`는 시군구 코드다

법정동 코드가 아니다. 99.7%가 시군구 5자리 + `00000`이고 distinct 값이 258개(시군구 수 262와 일치)다.

```
regionCode  5219000000   sigunguCode  52190   umd  도통동
```

**동은 `umd` 이름 문자열로만 존재한다**(채움률 100%). 조회는 `(sigunguCode, umd)` 쌍으로 한다.

### 3.2 드롭다운을 `Region` 테이블로 만들면 안 된다

`Transaction`의 (시군구, 동) 조합 5,285개 중 `Region` level 3에 이름이 일치하는 건 2,100개(40%)뿐이다.

**(a) 지방은 `읍면 + 리`가 통째로 들어온다** — 거래 건수의 10.5%
```
12130  "돌산읍 우두리"      Region level3은 "화양면, 남면, 화정면"
```

**(b) `Region` 쪽 결손·표기 차이** — 거래 건수의 22.0%. level 3에 법정동과 행정동(`상도동` / `상도1동`)이 섞여 있고 일부 법정동이 없다.

`Region`으로 옵션을 만들면 **선택해도 0건인 동이 대량 발생**하고, 거래가 있는 동의 상당수는 목록에 안 뜬다.

→ **옵션을 실거래 데이터 자체에서 만든다.**

### 3.3 옵션 임계값 — 3건. 이것은 오염 판정이 아니다

```
(시군구, 동) 조합 분포 (전체 기간)
  1~2건      340
  3~7건      527
  8건 이상  4,418
  합계     5,285

3건 이상이 덮는 거래 비율   99.993%
8건 이상이 덮는 거래 비율   99.962%
```

**임계값은 "목록을 채울 수 있는 동인가"를 거르는 실용 기준이지, 데이터 오류를 판정하는 기준이 아니다.** 8건으로 잡으면 정상적으로 거래가 뜸한 동 527개가 함께 잘린다. 3건이면 그들을 살리면서 거래의 99.993%를 덮는다.

**남는 오염을 인정한다.** 시군구↔동 쌍이 어긋난 소량 데이터가 있다.

```
봉천동     관악구 38,442건  ·  동작구      1건
사당동     동작구 18,792건  ·  관악구      3건
청량리동   동대문구 3,435건 ·  성북구      2건
```

3건 임계로 앞의 둘은 사라지고 사당동-관악구(3건)는 남는다. 거래 건수로는 0.007% 수준이다.

**비율 기반 검출은 시도했다가 버렸다.** "같은 시도에서 최대 건수의 1% 미만이면 오염"이라는 규칙은 20개 조합을 걸렀는데 **전부 오탐**이었다.

```
상동  이천시 140건  vs  부천 상동 16,235건    ← 둘 다 실재하는 동
중동  수원 팔달구 23건 vs 부천 중동 28,976건  ← 둘 다 실재
목동  경기 43건     vs  7,394건
```

같은 시도 안의 동명이인을 지운다. 쓰지 않는다.

남는 오염을 그대로 두는 근거: 우리는 **행정구역을 주장하지 않고 국토부 실거래 표기를 그대로 보여준다.** 그 3건은 원자료에 실제로 그렇게 적혀 있다. 출처를 명시하므로 사용자가 원본과 대조할 수 있다.

### 3.4 기간 제한을 두지 않는 이유

최근 3개월 기준 조합 4,117개 중 **8건 이상은 64.2%뿐**이다(중앙값 20건, p10 1건). 3개월로 끊으면 36%의 동에서 목록이 빈다. 기간 제한 없이 최신 N건을 가져오면 어디서든 채워진다.

**대가:** 오래된 거래가 섞인다. 그래서 날짜에 **연도를 반드시 표기한다**(§4.3).

### 3.5 성능

`[regionCode, contractDate desc]` 인덱스로 시군구 안을 최신순으로 걷다가 `umd`가 맞는 걸 N건 채우면 멈춘다.

```
강남구 율현동(강남구 거래의 0.4%) 최신 8건
  Index Scan using Transaction_regionCode_contractDate_idx
  Rows Removed by Filter: 3727
  Execution Time: 4.2ms
```

## 4. 공통 계층

### 4.1 조회

```ts
// lib/transaction/dong.ts (신규)
export interface DongTransaction {
  id: string;
  contractDate: string;       // 'YYYY-MM-DD'
  propertyId: string;
  propertyName: string;
  propertyType: PropertyType;
  exclusiveArea: number;      // ㎡
  floor: number | null;
  dealType: DealType;
  dealAmount: number | null;  // 만원, SALE
  deposit: number | null;     // 만원, JEONSE·WOLSE
  monthlyRent: number | null; // 만원, WOLSE
}

export async function getDongTransactions(opts: {
  sigunguCode: string;
  umd: string;
  dealType?: DealType;         // 미지정 = 전체
  propertyType?: PropertyType; // 미지정 = 전체
  excludePropertyId?: bigint;  // 상세에서 자기 건물 제외
  limit?: number;              // 기본 8
}): Promise<DongTransaction[]>;
```

**쿼리 규칙 네 가지.**

1. **`excludePropertyId`는 조회 단계 `WHERE`에 넣는다.** 가져온 뒤 거르면, 앞 N건이 전부 자기 건물일 때 다른 거래를 놓친다.
2. **취소된 거래를 제외한다** — `cancelDate IS NULL`. 해제 신고된 거래를 "최근 거래"로 보여주면 안 된다. 이 저장소가 이미 쓰는 규칙이다(`lib/transaction.ts:441`).
3. **정렬은 `[contractDate desc, id desc]`.** 같은 계약일 안에서 순서가 흔들리지 않게 한다. 저장소 관례와 같다(`lib/transaction.ts:29, 482`).
4. `regionCode = sigunguCode + '00000'`으로 인덱스를 태운다.

### 4.2 `Property`에서 `umd` 얻기

`Property`에 `umd` 컬럼은 **없다.** 대신 `address`가 `umd + ' ' + jibun`으로 조립된다(`lib/property.ts:93`). **마지막 토큰만 떼면 된다.**

```ts
export function umdOfProperty(address: string): string {
  return address.replace(/\s+[^ ]+$/, '');
}
```

```
"범어동 2272"        → "범어동"
"고촌읍 신곡리 100"   → "고촌읍 신곡리"     ← 실거래 umd와 같은 형식
```

**실측: 표본 3,000건 중 2,970건(99.0%) 일치.** 추가 조회가 없다. 불일치 1.0%는 한 매물의 거래가 여러 `umd`에 걸친 경우이고, 이때는 주소를 정본으로 본다.

**기존 `dongOfAddress()`(`scripts/ingest/apt-complex/match.ts`)를 쓰면 안 된다.** 그 함수는 **앞** 토큰을 뽑아 `고촌읍 신곡리 100` → `고촌읍`을 반환하는데, 실거래 `umd`는 `고촌읍 신곡리`라 지방에서 어긋난다.

### 4.3 표기 규칙 — 두 화면이 공유한다

**날짜는 연도를 포함한다.** `YY.MM.DD`.

기간 제한이 없어 2019년 거래가 목록에 올 수 있다(§3.4). `MM.DD`만 쓰면 몇 년 전 거래가 올해처럼 보인다. 이것은 취향이 아니라 정확성 문제다.

```
26.09.09   ✓
09.09      ✗
```

**금액**

```
매매·전세   9억 5,000만
월세        보증금 5,000만 / 월 150만
```

월세는 `5,000/150` 같은 축약을 쓰지 않는다. 보증금인지 월세인지 라벨 없이는 읽을 수 없다.

**면적** `84㎡`. **층** `11층`, 없으면 그 조각을 생략한다(`—`를 찍지 않는다).

**건물 유형**은 행에 표기하지 않는다. 대신 목록 전체가 하나의 유형으로 필터돼 있다(§5.3, §6.5). 섞어 놓고 유형 표기를 빼면 이름이 비슷한 아파트와 오피스텔의 가격을 같은 조건으로 오해한다.

### 4.4 빈 결과·로딩·실패 — 세 상태를 구분한다

| 상황 | 처리 |
|---|---|
| 최초 조회부터 0건 (상세) | 섹션 전체를 렌더하지 않는다 |
| 사용자가 필터를 바꾼 뒤 0건 | **패널과 필터를 유지**하고 `이 조건에 해당하는 거래가 없습니다` |
| 조회 중 | 목록 자리에 스켈레톤. 이전 결과를 남겨 두지 않는다 |
| 조회 실패 | `잠시 후 다시 시도해 주세요` + 다시 시도 버튼. "거래 없음"과 구분한다 |

필터를 눌렀는데 패널이 사라지면 사용자는 고장으로 받아들인다.

### 4.5 연속 요청 처리

지역을 빠르게 바꾸면 늦게 도착한 이전 응답이 최신 결과를 덮을 수 있다. **요청마다 시퀀스를 붙여 최신 것만 반영하고, 이전 요청은 `AbortController`로 취소한다.**

## 5. 상세 페이지 섹션

### 5.1 위치 — 「이 단지 가격 추이」 아래

```
1. 이 단지 최근 실거래 내역   (UnifiedTransactionTable)
2. 이 단지 가격 추이          (PriceCharts)
3. {동} 최근 거래             ← 신규
4. 면적별 실거래 비교 …
```

그 단지를 다 본 뒤 동네로 시선을 넓히는 순서다.

### 5.2 배선

```tsx
<DongTransactionSection
  id="dong"
  sigunguCode={property.sigunguCode}
  umd={umdOfProperty(property.address)}
  propertyType={property.propertyType}
  excludePropertyId={property.id}
  initialDealType={dealType}        // 위 섹션에서 선택한 유형
/>
```

- **기본 5건.** 상세는 이미 길다. 「{동} 거래 더 보기」로 확장한다
- **자기 건물 제외.** 바로 위 섹션이 그 건물의 거래를 이미 보여준다
- 거래유형 탭. **위 「이 단지 최근 실거래 내역」에서 선택한 유형을 초기값으로 받는다**
- 그 매물과 같은 `propertyType`만. 비교가 목적이다
- 서버 조회. 클라이언트 상호작용은 탭과 더 보기뿐
- 사이드바 목차 항목 추가 — 본문 렌더 여부와 같은 판정을 쓴다

### 5.3 제목

유형에 따라 말을 바꾼다. 빌라·오피스텔에 "단지"는 맞지 않는다.

```
아파트        문정동 최근 거래 — 같은 동네 다른 단지의 계약일순 내역입니다
빌라·오피스텔  문정동 최근 거래 — 같은 동네 다른 건물의 계약일순 내역입니다
```

### 5.4 표 형태

넓은 본문이므로 비교하기 쉬운 표로 놓는다.

```
계약일      건물명              전용면적   거래유형   거래가        층
26.09.09   올림픽훼밀리타운      84㎡      전세      9억 5,000만   11층
```

**단일 거래유형 탭을 선택한 상태면 「거래유형」 열을 생략한다.** 모든 행이 같은 값이라 자리만 차지한다.

빌라·오피스텔 상세도 같은 배선을 넣어 세 페이지가 갈리지 않게 한다.

## 6. 홈 패널

### 6.1 레이아웃

**두 칸 전환은 `lg`(1024px)부터다.** `md`(768px)에서 나누면 오른쪽이 약 270px가 되어 지역 선택 3개와 거래 목록을 넣을 수 없다. 기준은 화면 비율이 아니라 **오른쪽 패널의 실제 폭**이다 — 최소 380px를 확보한다.

```
lg 이상       왼쪽 62~65% : 오른쪽 35~38%   (grid-cols-[1.65fr_1fr])
lg 미만       세로 배치. 패널이 히어로 아래, 폭 100%
```

### 6.2 왼쪽 열 구성

**왼쪽 열은 세 덩어리다: 검색 히어로 + 바로가기 아이콘 + 통계 카드.** 오른쪽 거래 패널은 이 **왼쪽 열 전체와 나란히** 놓인다.

```
┌────────────────────────────────┬──────────────────┐
│ 📍 실거래가·생활권 정보 통합      │ 동네별 최근 실거래가│
│ 어디든, 임장ON에서 바로 검색하세요 │ 관심 지역의 거래 내역│
│ [검색창]                        │ [서울][송파구][문정동]│
│ 인기 지역 #송파구 #강서구 …       │ [아파트] [전체][매매]…│
│ [실거래가 찾기] [청약 일정 보기]   │ ─────────────────│
│ ───────────────────────────    │ 올림픽훼밀리타운 [전세]│
│ 🏢 🏬 🏘️ 🏫                     │ 84㎡·11층·26.09.09 │
│ 🌳 🏪 ⚡ 🏥                      │            9억 5,000만│
│ ───────────────────────────    │ …  8건             │
│ 📊 767만+  🏢 28.7만+           │ 송파구 아파트 매물 보기 →│
│ 🎓 1.3만+  🏪 62.2만+           │                   │
└────────────────────────────────┴──────────────────┘
```

**변경 내용**
- `StatsBar`를 히어로 **바깥에서 왼쪽 열 안으로** 옮긴다. 현재는 `<HeroSection />` 다음 형제로 놓여 있다
- 통계는 공간에 따라 **4열 또는 2×2**
- `TypeIconGrid`를 오른쪽 열에서 **왼쪽 열 아래**로 옮긴다
- **아이콘을 키우지 않는다.** 보조 탐색 수단이므로 높이를 줄여, 검색 영역이 아래로 길어지지 않게 한다

### 6.3 지역 선택

3단 캐스케이드. 시도·시군구는 기존 `/api/regions`를 그대로 쓴다(이미 5개 화면이 쓰는 검증된 패턴). 읍·면·동·리만 새로 만든다.

```
GET /api/regions?sido=서울&gu=1          → 시군구 (기존)
GET /api/dongs?sigunguCode=11680         → 읍·면·동·리 (신규)
GET /api/dong-transactions?...           → 거래 목록 (신규)
```

`gu=1`을 쓴다 — 실거래는 일반구 단위로 적재되므로 `/list`와 같은 기준이어야 한다.

**드롭다운 정렬은 가나다순이다.** 거래량순은 사용자가 특정 동을 찾을 때 위치를 예측할 수 없다. 거래량은 첫 화면의 기본 동을 고르는 **내부 기준으로만** 쓴다.

한 시군구의 동 개수는 중앙값 16개, p90 42.5개, **최대 89개**다. 40개를 넘으면 드롭다운 안에 입력 필터를 둔다.

### 6.4 읍·면·동·리 옵션 스냅샷

`/api/dongs`는 **ETL 사전계산 스냅샷**을 읽는다. 요청 경로에서 7.9M행에 `DISTINCT`를 돌리지 않는다. 홈 브리핑·인기지역이 이미 쓰는 방식이다.

```
DongOption { sigunguCode, umd, txCount }
   조건: 거래 3건 이상 (§3.3)
   저장: txCount 포함 — 기본 동 선정에 쓴다
   응답: 가나다순 정렬
   규모: 약 4,900행
```

일 1회 ETL에서 갱신한다. 동 목록은 거의 변하지 않아 하루 지연이 무해하다.

### 6.5 필터

```
[서울 ▾] [송파구 ▾] [문정동 ▾]
[아파트 ▾]  [전체] [매매] [전세] [월세]
```

**건물유형 select를 둔다.** 행에 유형을 표기하지 않으므로(§4.3), 섞어 놓으면 이름이 비슷한 아파트와 오피스텔의 가격을 같은 조건으로 오해한다.

**기본값은 `아파트` · `전체 거래`.** 첫 화면의 대상이 분명해진다.

폭이 충분하면 건물유형과 거래유형을 한 줄에, 좁으면 두 줄로 나눈다.

### 6.6 첫 화면

홈은 ISR(`revalidate = 900`)이다. 서버가 **인기 지역 1위 시군구의 `txCount` 최상위 동**을 골라 목록까지 프리렌더한다.

`PopularRegion`은 `{ sigunguCode, sido, sigungu }`라 동이 없다. 스냅샷에서 그 시군구의 최상위 동을 가져온다(§6.4가 `txCount`를 저장하는 이유).

드롭다운을 바꾸면 그때부터 클라이언트가 조회한다. 선택은 **URL에 반영하지 않는다** — 홈 URL을 오염시키지 않고 색인에도 영향이 없다.

### 6.7 목록과 더 보기

**8건**, 두 줄짜리 압축 형태.

```
올림픽훼밀리타운                    [전세]
84㎡ · 11층 · 26.09.09        9억 5,000만
```

읽는 순서는 **건물명 → 가격 → 면적 → 날짜·층**이다. 이름과 가격을 먼저 읽고 조건을 확인한다.

- 긴 건물명만 말줄임. **금액은 자르거나 줄바꿈하지 않는다**
- 층이 없으면 그 조각을 생략한다
- 건물명은 상세 페이지로 링크

**「더 보기」 링크.** `/list`는 **건물 목록**이고 동 필터가 없다. 거래 목록이 아니다. 따라서 버튼 문구를 도착 화면에 맞춘다.

```
송파구 아파트 매물 보기 →      →  /list?sido=서울&sigunguCode=11710&type=apt
```

`문정동 거래 전체 보기`라고 쓰면 동 단위 거래 목록으로 간다는 뜻이 되어 실제와 다르다. `/list`에 동 필터를 더하는 것은 **별도 과제**로 남긴다.

## 7. 검증

- **순수 함수** — `umdOfProperty` 경계(리 단위·`동1가`), 금액 표기(매매/전세/월세), `YY.MM.DD` 변환, 층 없음
- **쿼리** — `(sigunguCode, umd)` 정확 일치, 최신순 + `id desc` 보조 정렬, `propertyType`·`dealType` 필터, `excludePropertyId`가 **`WHERE`에** 적용되는지, `cancelDate IS NOT NULL`이 제외되는지
- **SSR 계약** — `renderToStaticMarkup`으로 0건·1건·8건, 월세 혼합, 긴 건물명, 층 없음을 렌더. 자리표시자가 새어나오지 않는지. 이 저장소에는 `@testing-library`가 없다
- **빈 결과 상태** — 최초 0건(숨김)과 필터 후 0건(유지 + 안내)이 실제로 갈리는지
- **홈 회귀** — 히어로 재구성이 검색·인기지역·CTA·아이콘·통계를 깨지 않는지. `tests/e2e` 홈 스펙 확인
- **배포 후 실측** — 드롭다운 옵션 중 0건 조합이 없는지, 리 단위 표기 노출 빈도, 홈 응답 시간 변화, `lg` 미만에서 세로 배치가 제대로 되는지

## 8. 배포

**애드센스 심사 중이다.** main에 머지하면 CI 통과 후 자동 배포되고 `web` 컨테이너가 재생성된다.

- 브랜치에서 작업한다
- **두 화면이 모두 준비된 뒤 한 번에 머지한다.** 배포를 1회로 줄인다
- 머지 전에 운영 데이터로 홈 화면을 확인한다. 홈은 심사 중 가장 많이 크롤링되는 페이지이고 이번 작업은 그 히어로를 재구성한다

## 9. 하지 않는 것

- `Region` 테이블을 고치지 않는다. §3.2의 불일치는 별도 사안이다
- `umd` 표기를 정규화하지 않는다. `돌산읍 우두리`를 `우두리`로 자르면 다른 리와 섞이고, 면 단위로 합치면 없는 집계를 만든다
- **비율 기반 오염 검출을 쓰지 않는다.** §3.3에서 오탐이 확인됐다
- 기존 `NearbyPriceComparison`을 바꾸거나 없애지 않는다. 제목만 정렬 기준이 드러나게 다듬는다
- `/list`에 동 필터를 더하지 않는다. 별도 과제다
- `lib/seo/indexable.ts`·`narrative` 계열을 건드리지 않는다. 이번 작업은 색인·메타 설명과 무관하다
- 홈의 다른 섹션(브리핑·청약 보드·허브)을 건드리지 않는다
- 새 데이터를 수집하지 않는다. 스냅샷은 기존 `Transaction`에서 파생한다
