# 5-2단계 · /faq 페이지 문구 개선(데이터 근거형)

- 작성일: 2026-10-23
- 상태: 승인(2026-10-23). 문구 시안 확정
- 문구 시안: `docs/superpowers/mockups/2026-10-23-faq-page.html` (숫자는 2026-10-23 운영 실측)
- 상위: [로드맵](2026-10-15-detail-public-data-roadmap.md) 5단계 · 앞 단계 [5-1 상세 FAQ](2026-10-21-detail-faq-dedupe-design.md)

## 1. 문제
`lib/faq/data.ts`의 공통 문항 약 40개(/faq와 목록 페이지 하단에 노출)는 1~2문장짜리 일반론이다. 어느 사이트에 있어도 같은 글이라 AI 티가 난다.

## 2. 방향(사용자 결정)
- 답은 임장ON이 실제로 하는 일과 가진 데이터로 쓴다. 다룰 내용은 어디서 언제 받는지(수집 시각·주기), 몇 곳·몇 건을 정리했는지, 무엇은 보여주지 않는지다.
- 숫자는 매일 새로 계산한다(방식 A). 부하 측정(운영 2026-10-22): 쓰는 집계는 관리비 단지 수(0.1초)를 빼면 모두 0.05초 미만이고, 하루 1회 캐시로 /faq와 목록 페이지가 함께 쓴다.

## 3. 구현
- `lib/faq/stats.ts` `getFaqStats()`: 아래 숫자를 한 번에 읽는다. `unstable_cache` 24시간을 쓰고, 실패하면 `null`을 반환한다.
  - 단지 수: 아파트·오피스텔·연립+다세대(`Property`, redirect 제외)
  - 관리비 공개 단지 수(`AptMaintenanceCost` distinct kaptCode)
  - 청약 공고 수, 결과 있는 공고 수, 무순위·잔여, 임의공급
  - 대출 상품 수, 전세보증 상품 수
  - 병원·약국·학교·어린이집(국공립 수), 공원·공영주차장·충전소
  - 실거래 총건수는 쓰지 않는다. 정확한 count는 0.86초, pg_class 추정치는 5% 오차라 문장에 넣기 부적절하다.
- `lib/faq/data.ts`: 답을 `string | ((s: FaqStats) => string)`로 바꾼다. `stats`가 null이면 숫자 문장 대신 숫자 없는 대체 문장을 쓴다(문항마다 지정).
- /faq 페이지와 목록 페이지 `<Faq category>`는 같은 `getFaqStats()`를 쓴다. /faq는 `revalidate = 86400`.
- /faq 상단에 "굵은 숫자는 매일 새로 계산합니다 · {기준일}"을 넣는다.
- 문항 구성: 12개 분야 38문항. 약국의 '출처는 무엇인가요'처럼 겹치는 문항은 합쳤다. 새 문항은 '아파트 상세에는 어떤 정보가 있나요', '경쟁률과 당첨 가점도 볼 수 있나요', '배정 초등학교는 어떻게 아나요'다.

## 4. 문구 규칙
- 답은 2~3문장이고, 문항마다 사실 하나(우리 숫자·수집 시각·제도 사실)를 넣는다. "~하는 것이 좋습니다"류 맺음말을 반복하지 않는다.
- 우리가 하지 않는 일을 분명히 적는다(호가 미제공, 신청 미대행, 위반건축물 미표시).
- 수집 시각은 install-timers.sh 기준 KST로 적는다(실거래 00·04시, 청약 03:30, 대출 매월 2일, 생활편의 매월 1일).
- 출처 표기는 `lib/data-sources.ts` 제공기관명과 맞춘다.

## 5. 테스트
- `getFaqStats`: 시드 DB 집계값, 실패 시 null.
- 문항 빌더: stats 있을 때 숫자가 들어가고, null일 때 숫자 없는 대체 문장. 금지 표현 부재.
- /faq SSR: 기준일 문구, 섹션 수. 목록 페이지 FAQ도 숫자 반영.
- e2e: 기존 FAQ 문구 검사 갱신.
