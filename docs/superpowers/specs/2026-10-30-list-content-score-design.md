# 목록 기본 정렬 — 상세 내용량(contentScore) 순 설계

- 상태: 설계 검토 중(구현 전). 2026-10-30
- 목적: AdSense 심사관·검색 크롤러가 목록 **기본 순서**대로 들어갔을 때 상세 내용이 많은 페이지를 먼저 만나게 한다.
- 범위: 매물(아파트·오피스텔·빌라, `/list`·허브), 병원, 약국, 어린이집, 학교, 공원, 주차장, 전기차충전소.
- 제외: 청약·금융상품(현행 정렬 유지), 상권 4종(비공개), 가이드(28편).

## 1. 결정 사항(사용자 확정)

| 항목 | 결정 |
|---|---|
| 방식 | A안 — 점수를 테이블에 저장, 배치로 갱신 |
| 서울 우선 | 위치가 있는 목록 전부. 지역 필터가 없을 때만 의미 |
| 정렬 키 | 매물: 서울 → 색인 대상(`isPropertyIndexable`) → 점수 → id / 나머지: 서울 → 점수 → id |
| 요약 문장(narrative) | 점수에서 제외(후속 작업에서 삭제 예정). 시설 색인 기준은 그 작업에서 재정의 — 이 점수를 기준으로 쓸 수 있게 저장 |
| 점수 구성 | 폭(블록 종류) + 깊이(정보량) |
| 사용자 정렬 옵션 | 기존 옵션(가격순 등) 유지, 기본값만 변경 |

## 2. 점수 원칙

1. **화면에 실제로 보이는 유효 정보만.** 컴포넌트가 `return null`이거나 "등록되어 있지 않습니다"·`-` 같은 빈 상태로 그려지면 0점. DB 값이 있어도 화면 조건(예: 단지 정보 타일 3개 이상, 건축물대장 `status='matched'`이고 타일·행 1개 이상)을 통과해야 점수.
2. **가중치:** 핵심 블록 2점, 부가 블록 1점, 깊이 0~4점.
3. **제외(모든 상세에 반복되는 것):** 브리핑, 관련 가이드, 출처 블록, 사이드바 목록, 요약 문장, FAQ(페이지 값을 다시 묻고 답하는 파생물이라 다른 블록과 이중 계산), Hero(항상 표시).
4. **주변 정보:** 실제 조회 결과가 있을 때 블록당 1점, **합계 최대 2점**(어느 유형에서도 최대 점수의 25% 이하).
5. **조회 판정 기준은 상세 화면과 같은 함수·같은 반경**을 쓴다. 상세 화면 로직을 SQL로 복제하지 않고, 작은 테이블은 화면 판정 함수(TS)를 배치에서 그대로 호출한다 → 화면이 바뀌면 점수도 따라감.
6. 판정 방식 표기: **정확**(화면 조건과 동일), **근사**(비용 때문에 대리 지표 사용 — 불일치 가능 항목 명시).

- 같은 층 비교: 거래 10건 미만 소규모 단지에서 같은 층 재거래가 있으면 화면엔 있는데 0점. 거래가 많아도 층이 전부 다르면 화면엔 없는데 1점(드묾).

- 거래 특이사항: 해제·이상치가 없는 거래 많은 단지는 화면엔 없는데 1점, 거래 1~2건인데 해제가 있으면 화면엔 있는데 0점.

## 4. 저장·정렬·계산

### 4.1 스키마(대상 8개 테이블: Property, Hospital, Pharmacy, Childcare, School, Park, Parking, EvCharger)
- `contentScore SMALLINT NOT NULL DEFAULT 0` — 위 점수표 합계(시설 색인 기준 재정의 때 재사용).
- `contentNearby SMALLINT NOT NULL DEFAULT 0` — 주간 배치가 채우는 주변 점수(0~2). 일간 배치가 주변 계산을 반복하지 않게 분리.
- `listRank INTEGER NOT NULL DEFAULT 0` — 정렬 전용 합성 키: `서울(1/0) × 10000 + (매물만) 색인 대상(1/0) × 1000 + contentScore`.
- 인덱스: `(listRank DESC, id)`. 매물은 필터가 걸리는 `(propertyType, listRank DESC, id)`.
- 컬럼 추가는 상수 기본값이라 PostgreSQL에서 메타데이터 변경만(테이블 재작성 없음).
- 배치 UPDATE는 **`updatedAt`을 건드리지 않는다**(사이트맵 lastmod·ISR 판단에 쓰이는 값 오염 방지). Prisma `@updatedAt`을 피하려고 raw SQL 사용.
- 서울 판정: 매물·병원·약국·어린이집·학교는 `sigunguCode LIKE '11%'`, 공원·주차장·충전소는 주소 접두어 `서울`(목록 지역 필터와 같은 규칙).

### 4.2 정렬 적용
- 필터 없는 기본 정렬: `ORDER BY listRank DESC, id`.
- 지역 필터가 있으면 서울 비트가 모두 같아 자연히 `색인 → 점수 → id`.
- 사용자가 고른 정렬(가격순 등)은 그대로. 허브(아파트·오피스텔·빌라 상위 30)도 기본은 `listRank`로.

### 4.3 배치(`scripts/ingest/content-score/runner.ts --entity=<이름> --mode=daily|weekly`)
- **daily**(자체 정보·집계 컬럼): 엔터티별 SQL 몇 개 + 작은 테이블 TS 판정. 바뀐 행만 UPDATE(`WHERE contentScore IS DISTINCT FROM 새값`). 해당 엔터티 수집 잡 뒤 또는 02:00~14:00 UTC 수집 없는 시간.
- **weekly**(주변 정보·학구도·건축물대장 전체 재확인): 공간 EXISTS를 2,000행 청크로, 청크 사이 쉬기, `nice`·`statement_timeout`·읽기 우선. 끝나면 `contentNearby` 갱신 후 `listRank` 재계산.
- 매물은 S1~S3(집계 정합성) 운영 반영 **이후** 적용(집계 컬럼이 점수 입력).
- 실행 기록은 기존 `IngestionRun`에 남긴다.

## 5. 예상 DB 부하(운영 통계 2026-10-30, pg_class 추정치)

| 테이블 | 행 수 | 크기 | daily 작업 | weekly 작업 |
|---|---|---|---|---|
| Property | 27.9만 | 543MB | 집계 컬럼 읽기 + AptComplex(2.2만)·관리비(3.8만) EXISTS + 건축물대장 변경분 | 공간 EXISTS ≤5종(최대 140만 탐색) + 학구도 ST_Contains(폴리곤 7천) |
| Transaction | 767만 | 4.6GB | **읽지 않음**(집계 컬럼으로 대체) | 읽지 않음 |
| BuildingRegister | 27.3만 | 507MB | 변경분만 TS 판정 | 전체 1회(청크) |
| Hospital(+하위 9개) | 8만(진료과 43.6만) | ~190MB | 하위 테이블 EXISTS·COUNT 집계 1회씩 | 공간 EXISTS 4종(32만 탐색) |
| EvCharger(+units) | 10.6만(55만) | 214MB | units 집계 1회 | 공간 EXISTS 3종(32만) |
| Pharmacy·Childcare·School·Park·Parking | 1.3만~2.6만 | 각 ≤34MB | 컬럼 읽기 | 공간 EXISTS 3~4종(합계 ~35만) |

- **daily 합계:** 순차 스캔 수 회(대부분 100MB 이하 테이블), Transaction 미사용. 예상 수십 초~수 분, CPU 1코어 이하. 쓰기는 점수가 바뀐 행만(평소 소수) → WAL 부담 작음.
- **weekly 합계:** 공간 인덱스 탐색 약 230만 회. GIST EXISTS 1회 0.05~0.3ms 가정 → **약 2~12분 CPU**. 박스가 2 OCPU이고 CPU 포화 이력이 있으므로 청크·쉬기로 30~60분에 걸쳐 분산, 수집 타이머가 없는 시간대에 실행.
- 모든 주변 판정 대상 테이블에 GIST 인덱스가 이미 있음(Property·Hospital·Pharmacy·Childcare·School·Park·Parking·EvCharger·Store·SubwayStation·TraditionalMarket·SchoolZone) → 새 공간 인덱스 불필요.
- 신규 B-tree 인덱스 8개(정렬용): 최대 27.9만 행, 생성 수 초. 마이그레이션 시 짧은 쓰기 잠금 → 수집 정지 시간에 배포.
- **수치는 추정치.** 구현 첫 단계에서 로컬 복원본(2026-10-28 운영 백업)으로 실측하고, weekly가 30분 CPU 예산을 넘으면 주변 판정을 격자(약 500m 셀) 사전 집계로 바꾼다(근사로 강등, 불일치 명시).

## 6. 검증 계획

1. **단위 테스트:** 엔터티별 점수 함수 — 블록마다 있음/없음/빈 상태(`-`, "등록되어 있지 않습니다") 케이스, 깊이 구간 경계, 주변 상한 2점.
2. **화면 일치 테스트(통합):** 시드 데이터에서 "점수 계산기의 블록 판정"과 "상세 페이지가 실제로 쓰는 판정 함수 결과"가 블록별로 같은지 비교. 정확 항목은 100% 일치가 기준.
3. **표본 화면 비교(로컬 복원본):** 유형별로 점수 상위 10·중앙 10·하위 10을 뽑아 로컬 dev 서버로 상세를 열고(운영 사이트 요청 없음) 블록별 실제 표시를 체크리스트로 기록 → 예측 대비 블록별 불일치율 표. 상위·하위 화면 캡처 2쌍씩을 보고서에 첨부.
   - 근사 항목(같은 층 비교·층별 프리미엄·거래 특이사항)은 불일치율을 따로 보고, 30% 초과 항목은 0점 처리 후 재측정.
4. **점수 분포 점검:** 유형별 히스토그램 — 한 점수에 70% 이상 몰리면 깊이 구간을 조정.
5. **배포 후(운영, 읽기 전용 DB 조회만):** 필터 없는 기본 정렬 첫 페이지 20개 — 매물은 전부 색인 대상인지, 시설은 점수 상위인지 확인. 사이트 HTTP 요청 버스트 금지.
